## 3. 再現記録v1

1対戦を、版を固定する`design`、試験意図を示す`test_plan`、開始前に固定する`input`、実施中／実施後の`record`へ分ける。

| 必須情報 | 保存場所 | 目的 |
|---|---|---|
| 版 | `rules_commit`、`rules_tree`、カタログhash、母集団snapshot | 後続改稿と混ぜず同じ本文へ戻す |
| 40枚デッキ | 各playerの`deck_order_top_to_bottom` | 枚数・カードID・順序を固定する |
| 先後 | `first_player`と各playerの`seat` | 先後差を集計する |
| 初手 | `initial_hand` | 山札上5枚との対応を固定する |
| 選択 | `declared_choices`とeventの`choice_ids` | 分岐判断を再生する |
| 支払い | eventの`payment` | 時、手札、準備、山札下を効果と分ける |
| 連鎖 | eventの`chain_id`、`link_index`、`responds_to_seq` | 発動・反応・解決順を戻す |
| 予約 | `reservation_id`、発生源、対象、期限、残回数、状態 | 発動元離脱後も残る効果と新個体を追う |
| 個体ID | 全カードの`instance_id` | 領域移動後の新個体、同名複数を識別する |
| 結果 | status、勝者、理由、完了ラウンド、最終そだち | 未実施・中断・完了を分ける |

イベントの前後状態は、同じ正規化手順で作る状態JSONのSHA-256を`before_state_sha256`／`after_state_sha256`へ記録する。v1では正規化実装をまだ固定していないため、実対戦を`completed`にする前に検査器側の正規化手順を追加する。記録者の文章だけで状態一致を主張しない。

## 4. 未実施fixtureの検査条件

`fixture-98-001`はschemaと入力検査のためだけに置く。

- A・Bとも40枚、上からの全順序、先後、そだち20、初手5枚を固定する。
- 80個の`instance_id`は全体で一意。各デッキは7種類すべてを含む。
- 現行452にあるカードIDだけを使う。未登録sourceの`I-c_dex`と`I-c_egg_normal`を含むため、別stratumを明記する。
- `record.status`は`fixture`、eventsは空、勝者はnull。机上局面、模擬対戦、実対戦、大量対戦のいずれにも加算しない。
- AとBが同じカード列でも個体IDは別。これは形式検査の簡単化であり、比較デッキの採用案ではない。

## 5. 今回固定した範囲

今回できたのは、母集団の採否境界と、再現記録に必要な箱である。まだ次を実施していない。

- 対戦エンジン、カード効果の自動解決
- P97-01〜06を再現する本番デッキと山札順
- completed記録のevent列、状態hash正規化、schema本体による意味検査
- 発動率、勝率、100到達ターン、操作秒数、予約数の測定
- 新12の登録、旧24・HOLD14・legacy4の復帰
- カード本文、同名制限、時、成果、探索枚数の改稿

したがって、98は大量対戦を行った記録でも、強度や全裁定を確定した記録でもない。

## 6. 次の再開地点

1. schema v1を読む最小validator／記録補助を作り、40枚、7種類、個体ID、先後・初手・山札順、event連番、連鎖参照、予約参照、状態hashの整合を検査する。
2. P97-01〜06ごとに単独、同名2枚、盤面エンジン併用のfixtureを分ける。新12を含む試験は別stratumを維持する。
3. 少数の手動対戦をcompleted形式で記録し、同じ入力から選択・支払い・連鎖・予約・結果を再現できるか先に確認する。
4. 記録形式が安定してから母数を増やし、実測後にのみ個別カードの改稿を判断する。

本文設計・全体監査→再現可能な大量プロキシ→非アート部分の凍結→最後にカード専用イラスト、の順を維持する。
