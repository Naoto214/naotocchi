### G-DE-01 / bubble-shooter / bug（判定ずれ・データ消失）
- **現象**: DROP_EVERY 発ごとの「1段降りてくる」処理で、既存の泡が**黙って消え**、残った泡は**半マス横にずれる**。行のつながり方（六角の隣接）も変わる。
- **根拠**: games.js:5356-5357
  ```js
  grid.unshift(Array.from({ length: COLS }, () => randColor())); // ぜんたいが 1だん さがる: ...
  for (let rr = 1; rr < grid.length; rr++) { const need = rowLen(rr); if (grid[rr].length > need) grid[rr] = grid[rr].slice(0, need); ... }
  ```
  `rowLen(r) = r % 2 ? 8 : 9`、`cellPos` の横オフセットも `r % 2` で決まる（5316-5317）。先頭に1行足すと既存の行はすべて偶奇が反転するので、(a) 9個の行が8個の行に変わって末尾の泡が `slice` で消え、(b) 全部の行の x が ±R ずれ、(c) `neighbors()`（5320）の隣接の対応が変わる。
  再現: `node evidence/scripts/de-bubble-drop.js` → 初期5段（泡43個）のとき、1回の降下で**3個消える**。(0,0) の x は 15 → 25。
- **判定**: 確定不具合（一意）。正本は同じ箇所のコメント「ぜんたいが 1だん さがる」（5356）と表示文 `say('⬇ 1段降りてきた!')`（5358）。どちらも「全体が下に1段ずれる」だけの動きを指していて、泡が消えたり横にずれたりする根拠はどこにも無い。
- **修正単位の設計**: 「六角グリッドの行偶奇オフセット」を1か所で持つ。`let parity = 0;` を追加し、`rowLen / cellPos / neighbors` をすべて `(r + parity) % 2` で判定する。降下するときは `parity ^= 1` にして、新しい行を `rowLen(0)` の長さで `unshift` するだけにする（既存の行は slice も pad もしない）。`nearestCell` と `ensureRow` も同じ `rowLen` を通るので、これで全部そろう。
- **影響範囲**: 点数式は変わらない。泡が消えなくなる分、赤線への到達がわずかに早まる（難易度がほんの少し上がる）。記録・セーブの互換に影響は無い。
- **回帰テスト案**: 降下ロジックを純関数 `dropRow(grid, parity, newRow)` に切り出し、node テストで「降下の前後で既存の泡の数が同じ」「各泡の画面 x 座標が変わらず、y だけ RH 増える」「隣接ペアの集合が同じ」を確かめる。

### G-DE-02 / lights-out / 表示不整合（「さいてい」が最小手数ではない）
- **現象**: HUD の「さいてい N」と終了時の「(さいてい N)」が、生成時に押した数 n をそのまま出している。5×5 のライツアウトは解が4通りあるので、真の最小手数が n より小さい場合がある。
- **根拠**: games.js:7480 `par = n; totalPar += n;`。HUD は 7478、終了文は 7498。`de-lightsout.js` で確かめた結果: 零空間の解の重みは {0,12,12,16}。n≤6 では常に n が真の最小。**n=7 では 0.4%、n=8 では 2.0% で n より少ない手数で解ける**。n = round(lerp(3,6,d)) + round なので、ふつう（d≤0.55）は n≤7（3問目だけ）、むずかしいは n≤8。
- **判定**: 確定不具合（一意）。ただし頻度は低い。正本はゲーム内の表示文「さいてい」（7478, 7498）、MINIGAME_CONTROLS「「さいてい」の手数をめざそう」（script.js:15034）、`'✨最少手数でクリア!'`（7482）。正しい値は「その盤面の真の最小手数」に一意に決まる。
- **修正単位の設計**: `gen()` の中で押した集合 S に零空間の基底2本（定数）をXORした4候補を作り、重みの最小値を par にする（25ビットのビット演算で済む）。`par` と `totalPar` にはその最小値を使う。
- **影響範囲**: n=7/8 の問題で par が1〜数手小さくなることがあり、eff（7497）がわずかに下がるので点数が最大で数点下がる。既存のベスト記録はそのまま（遡って直す必要は無い）。
- **回帰テスト案**: `minPressCount(grid)` を切り出して、ランダムな S について `minPressCount(apply(S)) <= |S|` が成り立つこと、既知の盤面（全点灯など）で既知の最小手数（全点灯は15）が返ることを確かめる。

### G-DE-03 / darts-board / 表示不整合（「おちつき」ゲージと実際の揺れの係数がずれる）
- **現象**: 照準の円と「おちつき」ゲージは `holdT² × 12` で描かれるが、実際の揺れは `holdT² × lerp(9,14,d)` で計算される。年齢が低いときはゲージが実際より揺れて見え、高いときは実際より落ち着いて見える。
- **根拠**: 表示は games.js:6590 `const amp = Math.min(26, holdT * holdT * 12)`、実際の値は 6573 `const amp = Math.min(26, holdT * holdT * lerp(9, 14, difficulty))`。赤に変わるしきい値（amp>12）も表示側の値で判定している。
- **判定**: 確定不具合（一意）。正本はゲーム内の表示（「おちつき」ゲージと照準円）。このゲージの役目は実際の揺れ幅を示すことなので、正しい値は実際の amp と同じ式に一意に決まる。
- **修正単位の設計**: update で計算した `amp` を変数に保存し、render はその値を読む（式を2か所に書かない）。他のゲームにも「表示用と判定用で同じ量を2回計算する」書き方があれば、同じ方針で1か所にまとめる。
- **影響範囲**: 表示が変わるだけ。点数・記録には影響しない。
- **回帰テスト案**: 小さいので目視で十分。テストを書くなら、ゲーム内部の amp を公開して描画の半径と一致するか確かめる。

### G-DE-09 / baseball-batting / bug候補（スイング判定がフレームレートに左右される。今回の再検証で見つけたもの）
- **現象**: スイングの判定は「押した時刻から40ms以内に来た update フレーム」でしか走らない。1フレームが40msを超える端末やタイミング（25fps未満、GCで止まったときなど）では判定が飛ばされる。ボールはそのまま通り過ぎて「からぶり!」になる（`swing ? 'からぶり!'`）。タイミングが完璧でも同じ。
- **根拠**: games.js:5126 `if (swing && now - swing.at < 40 && !ball.done) judge(); else if (ball.z < -0.08) { ... say(swing ? 'からぶり!' : ...)`。swing は 260ms まで残る（5131）。
- **確定させる手順**: Chrome DevTools の CPU 4x/6x throttle、または実機の低価格 Android で、ボールが到達する瞬間にスイングボタンを30回押す。「からぶり!」と表示されたのに `judge()` が呼ばれていない回数を数える（console.log を一時的に入れる）。1回でも出れば確定不具合になる。直し方は「swing を判定するまで消さない（`!swing.judged` を条件にする）」が一意に決まる。

### G-DE-10 / baseball-batting / 入力の誤判定（キャンバスを動かさずにタップすると意図しないスイングになる）
- **現象**: キャンバスに触れて4px未満で離すとスイングになる（5092 `if (!drag.moved) doSwing();`）。バットを動かそうとして触れただけでも、そのまま離せばスイングになる。ヒント（5081 / script.js:15008）には「画面を横になぞって、バットを球のコースへ」とあるだけで、画面タップでスイングすることは書かれていない（tennis/tank/bomber は「画面タップでもOK」と明記している）。

### G-DE-11 / animal-shogi / スコア式（時間切れ50 > 負けの上限45）
- **根拠**: games.js:4886 `w === ME ? clamp(100 - max(0,moves-12)*2,70,100) : w === AI ? clamp(18+moves,18,45) : 50`。4887 は `'時間切れ。引き分け'`。制限時間は mgDuration(60000)（4749）、みじかめなら42秒。自分の手番で考えたまま時間を流すと、負けるより点が高い。
- **判定**: 仕様判断要。正本（表示文）は時間切れを「引き分け」と定めているが、引き分けを負けより高く評価するのは設計として成り立つ。点数の順序を決めた正本は無い。
- **選択肢**: (a) 現状維持（引き分け>負け。時間を流すほうが得になる余地が残る）。(b) 引き分けを「負けの上限以下」にする（例: 40）か、「負けの式と同じ (18+moves) に +5」にして順序を負け<引き分け<勝ちのまま、時間を流す得を消す。(c) 時間切れを盤面の評価（駒得）で勝ち負けに振り分ける（evaluate を流用できる。仕様変更としては大きい）。
- 影響: (b)(c) では引き分けの点数が下がるので、これまでの記録との比較が甘くなる（記録の互換は問題ない）。

### G-DE-16 / ski-jump / 何もしなくても中位点が出る

- 影響: いずれも平均点が下がる方向に動く。

### G-DE-18 / fruit-slice / combo の区切り（指を離さない限り際限なく増える）

### G-DE-19 / fruit-slice / 説明文「落としすぎにも注意」に対応するペナルティが無い

### G-DE-20 / track-field（あわせて ski-jump）/ 制限時間が無く、入力が無いと終わらない

### G-DE-21 / picross-5 / 間違えたマスに自動で✕が付き、答えがわかってしまう

### G-DE-22 / picross-5 / ✕印のマスを塗ろうとすると、何度でもミスになる（今回の再検証で見つけたもの）
- **根拠**: `fill()`（6505）は `marks[y][x]` を確かめない。自動の✕が付いたマスをもう一度タップする、または、なぞって通過するたびに `mistakes++` される（6511 のなぞりでは通過したマスごとに fill が呼ばれる）。自分で付けた✕も、塗るのを防がない。
- **判定**: 仕様判断要。ヒントは「✕モードか長おしで、ぬらない印をつけよう」（script.js:15022）で、印が塗るのを防ぐとまでは書いていない。

### G-DE-23 / voxel-mine / 難易度の配線漏れ（ageDifficulty を取得しているのに使っていない）
- **根拠**: games.js:7122 `const difficulty = ageDifficulty();`。関数の中（7119-7213）で difficulty が出てくるのはこの1回だけ。地形生成（7141）、掘る速さ（HARD 7140）、制限時間はどれも固定。
- **判定**: 仕様判断要。README.md:153 は「年齢で上がる難しさの伸び」を難易度設定で抑えると書くが、ゲームごとに何を難しくするかは定めていない。
- **選択肢**: (a) マグマの率（0.04+d*0.06）に `lerp(0.8,1.3,difficulty)` を掛ける。(b) 鉱石の出やすさを難易度で下げる。(c) 変数を消して「難易度なし」を明示する。

### G-DE-24 / blackjack-21・yacht-dice・picross-5・puzzle-2048 / 難易度設定に反応しない
- **根拠**: 4関数（6815-6878, 7384-7458, 6480-6539, 5644-5717）の中に `difficulty` / `ageDifficulty` / `minigameEase` が1回も出てこない。picross と 2048 は mgDuration を通るので、やさしいでは時間だけ+20%になる。blackjack と yacht は制限時間も無いので、やさしい／むずかしいの選択が何も変えない。
- **判定**: 仕様判断要。全ゲームが難易度に反応すべきだという正本は無い。
- **選択肢**: (a) 運の要素が強いゲーム（blackjack/yacht）は難易度なしと明記する。(b) blackjack: やさしいではディーラーのヒント表示か、ディーラーが16で止まる。yacht: やさしいではターン数+1。picross: 問題プールを難易度で分ける。2048: 段階表を難易度でずらす。(c) 現状維持。

### G-DE-25 / hang-glider-3d / 機首角の保持がパッドと画面ドラッグで違う
- **根拠**: games.js:6646 `if (ky) pitch = ...; else if (!drag) pitch += (0 - pitch) * min(1, dt*1.5)`。`ky` は held（常に false）から作るので常に0。パッド（delta、6624）で入れた機首角は1.5/秒で0に戻るが、画面ドラッグ中（`drag` あり）は保持される。
- **判定**: 仕様判断要（どちらが意図なのか正本が無い）。Human QA で操作感を確かめるのもよい。
- **選択肢**: (a) パッドでも押している間は保持する（pad の押下状態を見る）。(b) ドラッグでも戻す（両方とも「離すと水平に戻る」で統一する）。(c) 現状維持し、ヒントに書き分ける。

### G-DE-26 / voxel-mine / コメント「うえに にげる」と実装（足もとのマグマを消す）の不一致（今回の再検証で見つけたもの）
- **根拠**: games.js:7167-7168 `function hurt() { ... // うえに にげる` → `if (py > 0) { map[py][px] = 0; } }`。プレイヤーは移動せず、踏んだマグマのマスが空気になるだけ。前回監査の「マグマに踏み込むと、そのマグマが消える」とも一致する。
- **判定**: 仕様判断要。コメントに合わせて上へ逃がすべきか（上が固い岩なら逃げられない）、コメントが古いだけなのかは一意に決まらない。
- **選択肢**: (a) コメントを「ふんだ マグマは きえる」に直す（挙動はそのまま）。(b) 上が空気なら1マス上へ戻し、マグマは残す（危険が残るので難しくなる）。

### G-DE-27 / tennis-rally・air-hockey・tank-battle / 最高点が100に届かない（今回の再検証で見つけたもの。minesweeper と同じ型）
- **根拠**: tennis 6451 `70 + 点差*8`、WIN=3 なので 3-0 で**94**。air-hockey 5996 `70 + 点差*7`、WIN=4 なので 4-0 で**98**。tank 6360 `78 + lives*7`、lives=3 なので**99**（bomber は 80+2*10=100 で届く）。どれも S（90）は取れる。
- **判定**: 仕様判断要（G-DE-14 と同じ理由）。
- **選択肢**: 共通ヘルパー `winScore(margin, maxMargin)` = 70 + 30*margin/maxMargin にする（4ゲームとも満点が100になる）、または現状維持。

### G-DE-28 / pipe-connect / 「少ないタップでつなぐと高得点」なのに、30タップまでは差が出ない
- **根拠**: games.js:6942 `solved >= ROUNDS ? max(0, 10 - max(0, taps - 30) * 0.5) : 0`。説明文は script.js:15027。30回以下なら何回タップしても同じ点数で、2問とも解かないとタップ数は点数に効かない。
- **判定**: 仕様判断要（30回を超えれば効くので、矛盾とまでは言えない）。
- **選択肢**: (a) 基準を「最短手数＋α」（生成した経路から計算できる）にする。(b) 説明文を「タップしすぎると少し減点」に弱める。(c) 現状維持。

### G-DE-29 / match-3 / 連鎖の途中で時間切れになると、残りの連鎖の点が入らない
- **根拠**: 連鎖は setTimeout の段階処理（6161-6172）で進み、各段は `if (!running) return;` で止まる。時間切れの判定（6187）は連鎖の途中でも finish する。
- **判定**: 仕様判断要。時間切れで打ち切ること自体は自然。
- **選択肢**: (a) 時間切れになったら入力だけ止め、連鎖が終わってから finish する（`busy` を待つ）。(b) 現状維持。

### G-DE-30 / ring-flight-3d（summer も）/ 何もしなくても中位点が出る
- **根拠**: 機体の初期位置は (0,0)。リングは x∈±0.8、y∈±0.7 に出て、半径は lerp(0.48,0.38,d)（5212-5215）。面積比で計算すると、何もしなくても約25〜32%のリングをくぐる。25秒で約19個のリングが出るので、5281 の式に当てはめると**推定で約50点**（前回監査の推定40〜50点と一致。実測はしていない）。

- **選択肢**: (a) 点数式の切片（15）と「成功率*20」を下げる。(b) リングの出現位置を、中央を避ける分布にする。

## E. 誤検出

### G-DE-31 / ring-flight-3d・submarine-3d・hang-glider-3d・asteroids-classic / 「未使用の held 分岐」はバグではない
- **根拠**: held は各ゲームの中だけの変数で、ring-flight 5192/5221、submarine 6015/6043、hang-glider 6615/6645 では一度も書き換えられない。asteroids（7311/7336）では thrust だけが 7320 で設定され、left/right は書き換えられない。キーボード操作は data-key ボタンへの合成 pointer イベント（script.js:3329）で届くので、held を経由しない。
- **判定**: 誤検出（挙動には影響しない死にコード）。整理するのはリファクタリングの工程でよい。注意点として、hang-glider では `ky` が常に0なので 6646 の `else if (!drag)` の減衰が必ず働いている（これが G-DE-25 の原因。死にコードとは別の問題）。

### G-DE-32 / lights-out / 「全消灯で gen を再帰すると totalPar が二重に加算される」
- **根拠**: 7480 で `totalPar += n` を足した後に再帰する、という構造自体はそのとおり。しかし全消灯になるのは押した集合が零空間の元のときだけで、その重みは12か16（de-lightsout.js）。n は最大8なので、**この再帰に到達することはない**（各 n で2万回試行して0件）。
- **判定**: 誤検出（潜在的な不具合としては正しいが、現行のパラメータでは到達しない）。G-DE-02 で gen を直すときに、加算を再帰の後に移しておけばよい。

### G-DE-33 / hang-glider-3d / 「着陸しない方が +8 点」
- **根拠**: 6705 `(landed ? 0 : 8)`。ヒント 6620 / script.js:15024 は「地面につくと終わり」で、着陸は早期終了（失敗側）として説明されている。最後まで飛び続けたことへの加点は、正本と矛盾しない。
- **判定**: 誤検出。

### G-DE-34 / billiards-6 / 「ヒントは『白いボールから』と書くが、どこからでも引ける」
- **根拠**: 4643-4651。ショットはドラッグのベクトルだけで決まる。ヒントどおり白球から引けば、ヒントの説明どおりに動く。実装のほうが広く受け付けているだけで、ヒントに従った子が戸惑うことは無い。
- **判定**: 誤検出（説明と実装の食い違いで実害が出るものではない）。

## 気づき
1. 確定（一意）は bubble-shooter の降下だけが実害の大きいバグ（泡が消える）。lights-out と darts は表示の正確さの問題で、影響は小さい。

3. baseball の判定が「押した直後の update フレームから40ms以内」に依存している点は、前回監査で見落とされていた。低スペック端末で検証する価値が高い（G-DE-09）。

5. 範囲外だが関係するもの: README.md:153 は難易度の伸びを「やさしい0.4倍・ふつう0.7倍」、みじかめを「90秒以上を6割」と書くが、実装（script.js:2943-2957）は 0.3/0.55、「20秒以上を0.7倍」。README のほうが古い。担当の付録で「みじかめ 42秒」としている計算は実装どおりで正しい。README を正本として扱う他の担当は注意が必要。
