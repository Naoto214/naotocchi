# 発想型ステージ制作テンプレート

## 提案時に埋める項目

- 恒久ID／revision／章／仮難易度／既存ルール一覧。
- 1面1発見: 「プレイヤーは何を思い込み、何に気づくか」を1文で書く。
- 数字合計・出口の整数分解・最終状態からの逆算。
- 必須にしたい操作と、その操作を省略できない理由。
- 2〜4種の構造を手で定義し、数字・出口・門条件・高さの少数派生を生成する。
- 見た目の情報量: 岩・門・トゲの数、役割、削除可能性、8×8内での数字の読みやすさ。
- 確認済み解答と最短証明の有無。解答未確認は採用不可。

## 探索／採用前チェック

1. 必ず本番と同じengine.moveで探索し、別の簡略物理を正解判定に使わない。
2. 保存キー、状態同値キー、時間や外力の有無を確認する。将来の波／光線では時刻・周期・イベント状態も同値キーへ含める。
3. 小さい盤面はBFS、広い状態空間は上限つき探索で解答を探す。非許容ヒューリスティックはA*の最短保証と呼ばない。
4. 解答を最初から再生し、全員脱出、質量、門占有、不変地形を検査する。
5. 局所BFSで往復・無駄な待機・同じ盤面へ戻る部分を短縮する。
6. noMerge / noSplit / noOverflow / noFall / noSupport / noGate 等の除外探索を行う。exhausted・limit・solvedを明確に分ける。
7. 合法な斜め迂回はエンジン変更で塞がず、必要なら地形を修正し再探索する。
8. 出口の再利用による全8帰還、初手の単純合体、片側のトゲ未使用などの短絡方針を明示的に試す。
9. 全7面で必要な発想と解法骨格を比較し、同じ入口／分裂／回収だけの繰り返しになっていないか確認する。
10. Undo・リトライ・途中保存・B方式継続を実sessionで再生する。最終配信には解答を含めず、監査資料へ保存する。

## 難易度の評価表

各項目を0〜3の仮評価で記録する。合計点を人間の難易度と同一視しない。

|観点|0|3|
|---|---|---|
|発想の反転|目標へ直接進む|一度小さくする／出口から離れることが必要|
|先読み|次の1操作だけ|回収後の支え消失まで複数段階を考える|
|数の再構成|既存数字の運搬|通過用と帰還用の数字を分けて組み直す|
|依存関係|各キャラが独立|支える役・通る役・回収役が相互依存|
|見つけにくさ|誘導通り|自然な方針が行き詰まり、別の視点が必要|
|公平性|隠れた条件や狭い操作精度が必要|表示と既知ルールだけで説明できる|

手数、visited、elapsedだけで★を決めない。分岐数は成功操作数と状態同値で数え直す。最短解本数を数えていない場合はunknownと書く。dead endはUndoで戻れるかを確認し、無意味なやり直しを難易度に含めない。

## 本人試遊の記録

- 面番号、端末・Safari版、表示幅、初見時間、解けた時間、ヒント段階。
- 最初に立てた方針、行き詰まった理由、気づいた瞬間を短い言葉で記録。
- 「分かったが指で操作できない」と「解法が分からない」を分ける。
- 手数だけでなく、楽しさ・納得感・理不尽さ・疲労・既視感を聞く。
- 想定より簡単なら、合法な近道を保存して発想が省略される理由を調べる。
- 難し過ぎる場合は先に3段階ヒントを調整。新ルールや障害物を足す前に盤面を整理する。

## 採否記録

候補名／構造／想定発想／確認済み解答／最短証明／除外探索／短絡／操作性／採否と理由。
「長いから採用」「探索時間が長いから超難問」は禁止。実機前は仮評価。

node prototypes/naopoyo-chapter2/design/verify.mjs

node prototypes/naopoyo-chapter2/design/ablate.mjs /tmp/ablation.json
node prototypes/naopoyo-chapter2/design/compare.mjs /tmp/candidates.json
