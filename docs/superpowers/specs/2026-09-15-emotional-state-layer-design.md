# 感情状態レイヤー設計

2026-09-15。なおとっちのホーム画面で、パラメータや「!」を読まなくてもキャラクターの状態がある程度わかり、世話をした時に「数値が回復した」ではなく「この子が楽になった／喜んだ」と感じられることを目的とする。基準mainは `e789e61e60973da631d6f26a5bc1e1ee385d955c`。

## 目的

現在の注意喚起は `care-status.js` と `care-attention.css` により成立しているが、UI通知が中心で、キャラクター自身から状態が読み取りにくい。新設する感情状態レイヤーでは、既存の判定・モーションを再利用し、キャラクターの姿勢・動作頻度・一時リアクションで状態を伝える。

「状態」と「されたことへの反応」は分離する。

- persistent state: 現在のパラメータから導出され、条件が続く間は弱く継続する。
- temporary reaction: ごはん、じゃれる、薬、睡眠などの直後に短時間だけ出る。persistent state より優先し、終了後に状態を再評価する。

感情状態はセーブデータへ永続保存しない。既存パラメータから毎回導出する。

## 既存責務との境界

### care-status.js

状態判定の正本。病気、いのち、けんこう、空腹、げんき、ごきげん、うんち等の既存閾値を感情レイヤー側で重複定義しない。

第1段階では `care-status` の結果を、表示用の感情カテゴリと強度へ変換する。軽度表現に追加閾値が必要な場合も、判定責務は一か所へ寄せる。

### emotion resolver

新しい小さな純粋ロジック層。DOMや保存処理を持たない。

入力: care-status由来の状態、必要最小限の現在値、睡眠中か等。
出力: `state`, `severity`, `motionProfile` 等の表示用情報。

第1段階の状態候補:

- normal
- hungry (mild / strong)
- unhappy (mild / strong)
- tired (mild / strong)
- sick
- weak (mild / critical)
- wantsPlay

求愛は第2段階。既存の求愛成立条件をコピーせず、既存ロジックの結果だけを受け取る。

### cast-motion.js

実際の動きの正本。既存の `bounce`, `wiggle`, `shy`, `love`, `droop`, `settle`, `shake`, `munch`, `doze`, `stretch`, `nod`, `curious` 等を優先利用する。

感情レイヤーのためだけに大規模な別アニメーション基盤を作らない。

### social reactions

第2段階。メインのイベントを見て恋人・仲間が反応する。恋人・仲間へメインの状態をコピーしない。

## 状態優先順位

同時に複数条件が成立しても、ホームで強く見せる persistent state は基本1つとする。

優先順位:

1. いのち危険
2. 病気
3. けんこう低下
4. げんき低下
5. 空腹
6. ごきげん低下
7. じゃれたい
8. 通常

求愛を追加する第2段階では、病気・弱りなどの上位状態中は求愛しぐさを抑制する。

上位状態が解決した後、まだ別の問題が残っていれば次の状態へ自然に切り替える。

## 第1段階の表現

### normal

通常待機。常時大きく動かさない。既存idleを壊さず、低頻度の小さな変化に留める。

### hungry

mildでは少し落ち着かない、食べ物を気にする印象。strongでは姿勢をやや落とし、`droop` を弱く使う。ごはん直後は `munch` を最優先し、十分回復した場合のみ小さな `bounce` を続ける。

### unhappy

mildでは静か、少しそっぽを向く印象。strongでは `settle` / `droop` を弱く利用。じゃれた直後は `wiggle` または `bounce`。

### tired

動作頻度・速度を落とし、時々 `doze`。強いほど派手に動かさない。睡眠後の起床時は `stretch`。

### sick

`droop` を基調に、既存の汗表現を維持。時々小さな `shake`。治療成功時は `settle` を挟み、治癒した場合だけ小さな喜びへつなぐ。薬そのものを毎回「大喜び」にはしない。

### weak

弱るほど動作半径と頻度を下げる。criticalではほぼ静止に近づけ、激しい警告アニメーションをキャラクター本体へ足さない。UI側の既存 critical 表示は残す。

### wantsPlay

悪い状態として扱わない。通常状態を保ったまま、低頻度で `curious` / 小さな `bounce` 等を出し、プレイヤーへの興味として見せる。病気や弱りが優先される時は抑制する。

## temporary reaction のルール

世話操作では「行動 → 感情 → 余韻」の3拍子を目標にする。

- ごはん: `munch` → 状態再評価 → 十分回復なら小さな喜び
- じゃれる: `wiggle` / `bounce` → 状態再評価
- 薬: 小さな拒否・驚き → `settle` → 治癒時のみ安堵・小さな喜び
- 睡眠: `doze` → 起床時 `stretch`

リアクション中は persistent state を一時停止する。リアクション終了後、最新状態を再評価する。

`persistent state < temporary reaction` を明確な優先関係とする。

## 表情画像の扱い

第1段階では新しい顔差分を必須にしない。248形態へ多数の表情PNGを一括追加しない。

まず既存PNGのまま、姿勢、動作頻度、速度、汗、向き、モーション、リアクションのタイミングだけで効果を確認する。

第1段階の実機確認後、必要なら1種×8段階で `normal / happy / distressed / grumpy / shy` 程度の表情差分を試作し、効果が大きい場合のみ拡張する。

## 第1段階の受け入れ基準

1. 病気・空腹・げんき低下・ごきげん低下・いのち低下・じゃれたいが、パラメータ表示や「!」を見なくてもホーム上のキャラクターの動きからある程度区別できる。
2. 状態表現は常時激しくループせず、通常時の落ち着きを壊さない。
3. いのち低下・強い疲労では、状態が悪いほど動きが激しくなるのではなく、動作量が減る。
4. ごはん・じゃれる・薬・睡眠の主要世話操作で、操作直後に明確な一時リアクションが出る。
5. 一時リアクション中に persistent state のモーションが重なって、不自然な同時演技にならない。
6. リアクション後に最新のパラメータを再評価し、未解決なら次の状態表現へ戻る。
7. `care-status.js` の既存閾値と矛盾する独立判定を別ファイルへ複製しない。
8. 既存の「!」、care alert、critical表示は削除せず、補助情報として維持する。
9. 既存セーブとの互換性を壊さず、感情状態のための必須永続フィールドを追加しない。
10. reduced-motion利用時は既存方針を守り、状態が伝わらなくなる場合は静的な姿勢・既存UI補助で代替する。
11. iPhone実機で、メインキャラを見た第一印象として「何か困っている／眠そう／病気そう／遊びたそう」がUIを読む前に認識できることを確認する。
12. 26体の仲間が存在するケースでも、第1段階では仲間全体を連動させず、既存レイアウト・性能・視認性を悪化させない。

## 第1段階の対象外

- 恋人・仲間の社会リアクション
- 求愛したそうなしぐさ
- 仲間ごとの性格係数
- 全キャラの表情差分量産
- AI会話連動
- セリフ体系の大規模刷新

これらは第1段階の実機確認後に第2段階として設計する。

## テスト方針

既存の `care-status-test.cjs`, `care-status-integration-test.cjs`, `cast-motion-test.cjs` を維持し、感情resolverにはDOM非依存の単体テストを追加する。

最低限、状態優先順位、mild/strong境界、temporary reaction優先、リアクション終了後の再評価、reduced-motion時の安全なフォールバックを検証する。

ブラウザ統合テストでは、主要世話操作後に期待するreactionが1回だけ起動し、persistent stateへ戻ることを確認する。

## 実装順

1. emotion resolver と単体テスト
2. メインキャラの persistent state 表現
3. 世話操作の temporary reaction 接続
4. 優先制御と再評価
5. reduced-motion / 既存alertとの整合
6. iPhone実機確認

第1段階が「生きている感」に十分効くことを確認した後に、第2段階として恋人・仲間の社会反応、求愛、性格差、必要なら表情差分を設計する。
