# VERSION 4：座標系と比較ページの表示範囲の監査

2026-11-15。原因調査の記録。背景、カメラ、キャラクター、アイテム、歩行判定の製品コードはこの調査では変更していない。

## 結論

左右の描画保護境界が右へ平行移動した事実は確認できなかった。一方、**歩行ポリゴンと背景画像は異なる座標投影を使っており、画面に見える床と歩行可能領域は一致していない**。さらに、VERSION 3比較ページは固定幅iframeを余白のある親要素に置くため、390pxの親画面で右端が欠ける。これらは経路探索による停止とは分けて扱う必要がある。

この記録は座標の検証であり、移動可能範囲を広げたという報告ではない。実際のドラッグによる到達位置・経路停止は別の診断結果を参照する。

## 足元・ポインター・カメラの関係

4版とも同一条件で `scaleX=0.6342010144285222`、`scaleY=1.2814324050630237`、`bodyScale=1` となった。位置は縦横別倍率で配置するが、人物描画は逆倍率で補正し、絵そのものの比率を保つ既存設計になっている。

nativeの足元を `(nx,ny)`、stageのvirtual原点を `(L,T)`、presentationの原点を `(px,py)` とすると、画面座標は次の通り。

```text
screenX = px + (L + nx - px) * scaleX
screenY = py + (T + ny - py) * scaleY
```

ポインター入力では `unscalePoint()` がこの式を逆変換し、その後stage原点を引く。参照：[`home-production-touch.js`の`unscalePoint`・`presentationRect`](../../../home-production-touch.js#L289)、[`home-production-diorama.js`の`point`](../../../home-production-diorama.js#L620)。測定点の往復誤差は約`5.7e-14` CSS/native px程度で、右だけずれる丸め・符号の誤りは確認できない。

4体・装着ありのV3左ドラッグ例では、描画保護境界はx=109.924483～280.072069、中心194.998276。表示フレーム中心194.998276と一致する。実到達足元x=175.339769から左へ0.75 CSS pxを調べると歩行ポリゴンが不許可となり、描画保護・遮蔽・他個体との接触の条件は許可だった。描画保護境界まで約65.42pxあることから、この地点の制約を「左右安全余白のずれ」だけでは説明できない。

ただし、これは到達点の先を0.25px刻みで調べた局所診断であり、実行中に停止したイベントや全域の到達不能の証明ではない。経路ログと合わせて解釈する。

同じ測定で描画矩形中心と足元の差はx=+1.168601px、y=−48.465521px。衝突楕円は足元中心であり、画像矩形中心を衝突中心にする設計ではない。画像中央が足元より上にあること自体は座標不良ではない。

## 背景と歩行ポリゴンの異なる投影

[`home-production-world.mjs:13`](../../../home-production-world.mjs#L13)の`geometry()`は`presentationRect()`を通じてvirtual worldを取得し、歩行系に使う。一方、[同ファイル30～43行](../../../home-production-world.mjs#L30)の`fullBackdrop`描画は実DOMの矩形を使って画像全体をcover配置する。

実DOMとvirtual worldの実測値：

| 対象 | left | top | width | height |
|---|---:|---:|---:|---:|
| 実`.home-living-world` | 0 | 0 | 390 | 844 |
| virtual world | 119.244897 | −62.406250 | 358 | 688 |
| 実画像cover | −86.333333 | 0 | 562.666667 | 844 |

歩行系の[`artTransform()`](../../../home-art-navigation.mjs#L3)は、幅をvirtual領域から求め、高さを幅×1.5とし、`stage.top + stage.height − height×0.94`に画像上端を置く。この結果を人物用カメラで画面へ変換する。背景coverは実画面の幅・高さから別に求める。

今回の同一正規化背景座標 `(x,z)` に対する画面位置は以下になる。

```text
歩行系：X =  81.478018 + 227.030614 * x
        Y = −99.558461 + 688.088744 * z

実画像：X = −86.333333 + 562.666667 * x
        Y =   0        + 844        * z
```

| 同じ背景座標(x,z) | 歩行系の画面位置 | 実画像の画面位置 | 差（歩行系−実画像） |
|---|---:|---:|---:|
| (.47,.53) | (188.182407,265.128573) | (178.120000,447.320000) | (+10.062407,−182.191427) |
| (.60,.53) | (217.696387,265.128573) | (251.266667,447.320000) | (−33.570280,−182.191427) |
| (.47,.96) | (188.182407,561.006733) | (178.120000,810.240000) | (+10.062407,−249.233267) |
| (.60,.96) | (217.696387,561.006733) | (251.266667,810.240000) | (−33.570280,−249.233267) |
| (.34,.53)：旧上端の頂点 | (158.668427,265.128573) | (104.973333,447.320000) | (+53.695094,−182.191427) |
| (.49,.96)：旧下端の頂点 | (192.723019,561.006733) | (189.373333,810.240000) | (+3.349686,−249.233267) |

歩行系の横幅は実画像の40.35%、縦幅は81.53%。左右への一定量の平行移動ではない。nativeとポインターの往復変換が正しくても、この画像との不一致は残る。

この分離は既存コードに意図が明記されている。[`home-production-touch.js:530`](../../../home-production-touch.js#L530)に「Background coverage is independent of the resident-safe presentation」、[`home-production-world.mjs:65`](../../../home-production-world.mjs#L65)に「Native navigation, floor polygons and sprite foot coordinates are unchanged」とある。V1～V3の新しいカメラ不具合とは区別する必要がある。一方、背景に見える舗装に沿って動けるようにするという目的には構造的な不一致がある。

さらに、[遮蔽処理](../../../home-production-world.mjs#L64)はV17/V18表示で実画像coverの位置から人物カメラを逆変換している。遮蔽は実背景に合わせられているが、歩行ポリゴンはvirtual投影に残っている。歩行判定と遮蔽判定が同じ背景正規化点を同じ画面位置として扱っているわけではない。

## 比較ページのiframe切れ

[`tools/home-movement-v3/page.css`](../../../tools/home-movement-v3/page.css#L1)では狭い画面のmainに左右12px、`#play-wrap`に左右8pxの余白がある。iframeは390pxの固定幅で、[`page.js`](../../../tools/home-movement-v3/page.js#L6)も選択した320/375/390/430pxを固定設定する。

390px親画面、390px試遊幅、横スクロール前の実測：

| 要素 | left | right | 幅 | scrollWidth |
|---|---:|---:|---:|---:|
| main | 0 | 390 | 390 | 390 |
| play-wrap | 12 | 378 | 366 | 406 |
| iframe | 20 | 410 | 390 | 390 |

横スクロール範囲は40pxで、初期位置ではiframe右端32pxが親要素に隠れる。40pxはスクロール範囲であり、初期の画像欠け量32pxとは区別する。ユーザーのスクリーンショットで右UIが欠ける現象と整合するが、スクリーンショットだけから端末のCSS幅・拡大率・スクロール位置までは確定できない。

iframeの中のラベルはiframe内CSS pxであり、外側のスクリーンショットのピクセル位置へ直接置き換えてはいけない。この切れはゲーム内部の描画保護境界とは別問題である。

## 再現方法と出力

```sh
# 未使用の出力先に検証用コピーを作る。製品ファイルは変更しない。
node tools/home-movement-v4-audit/build.cjs /tmp/v4-audit
REACH_DIST=/tmp/v4-audit REACH_OUT=/tmp/v4-coordinates node tools/home-movement-v4-audit/coordinates.cjs
```

既存の検証用コピーがある場合は1行目を省略し、`REACH_DIST`にその場所を指定する。Playwrightの場所は`PLAYWRIGHT_MODULE`、Chromiumは`CHROMIUM_PATH`で指定できる。既定値はこの作業環境のインストール先。画像が不要なら`COORDINATE_OVERLAY=0`を指定する。

出力は`coordinates.json`（4版の実DOM・virtual矩形・投影点・往復誤差・iframe計測）と`polygon-projections.png`。画像の水色実線は従来のcityポリゴンを歩行座標で投影した輪郭、ピンク破線は**同じ頂点列**を実画像coverで投影した輪郭。白線は同一正規化点の対応を示す。投影だけを比較するため、V3で追加した小さな領域はこの輪郭に含めない。ピンク破線はUIの背後にも及ぶため、これをそのまま移動可能にする提案ではない。canvasは使い捨てのブラウザ文書にだけ追加し、アプリには組み込まない。

ビルドのD版は`REACH_DIST`を作成した時点の作業ツリーから生成される。JSONに記録する歴史的コミットのハッシュと、D版検証用コピーの出所は区別する。V3固定の測定を再現するときはV3コードから生成したコピーを使う。

## 制約と安全な次段階

- 実機Safariのピンチズーム、ブラウザバー、Safe Areaの動的変化はこのChromium測定では検証していない。
- この数値は390×844・4体・stage5等の固定条件。別の人数・端末寸法では人物カメラの係数が変わり得る。
- 13地域・4時間帯の実背景とポリゴンが自然に一致することを、この一例で証明するものではない。
- 単純に歩行投影をcoverへ置き換えると今回の点は182～249px下へ移り、従来経路、深度、セリフ・UI保護に影響する。移動境界の一括置換やカメラ変更は行わない。
- 次の背景調整を検討する場合は、まずこの重ね合わせを基に、現在の安全な経路と位置を保持しながら、画面の舗装・遮蔽・76pxセリフ領域・描画余裕をすべて満たす追加候補だけを調べる。今回別途試作する経路回帰修正と混ぜずに評価する。
