# VERSION 4 調査：描画範囲・足元・接触判定の中心

2026-11-15。従来版 A と VERSION 3 D の読み取り調査結果。ここで扱う PNG、CSS、境界計算、接触判定には変更を加えていない。経路の回帰試作とは分けて記録する。

## 結論

代表条件では、V3 の描画保護境界は画面中央と一致し、左右両方へ広がっている。左だけを狭くする新しい装着物の余白は確認されなかった。右の拡大量が大きい一因は、従来版が右側の装着物の余白を大きく取っていたことにある。

一方、ヤドカリ画像を左向きに反転すると、描画矩形の中心が足元から約 1.17 CSS px 右へずれる既存の CSS 優先順位の問題を確認した。従来版にも V3 にも存在する。移動座標や接触判定の中心は動かないため、この修正だけで左方向の実到達位置が大きく改善するとは判断できない。

4 体配置の左端は、描画保護境界から約 65 CSS px 内側で止まっている。同じカメラを保持して他個体を除くと、左側の描画保護境界付近へ到達する。表示上の左右差を描画境界だけで説明できず、歩行可能領域、他個体の位置、そこへ至る経路を分けて調べる必要がある。

## 測定条件と読み方

- 生データ：調査時点の `diagnostics.json.gz` の `equipped`。
- Chromium、390 × 844 CSS px、下 Safe Area 模擬 34px、とかい夜。
- ヤドカリ `hermit_crab/06.png`、トイレットペーパー、パンダ・アザラシ・ゴリラを含む 4 体。
- A/B/C/D 間で同じ初期配置とカメラを使用。A は従来版、B は V1、C は V2、D は V3。
- `solo_same_camera` は他個体を取り除くが、カメラとヤドカリのサイズは 4 体時のまま保持する切り分け条件。通常の 1 体構成に再レイアウトした画面ではない。
- 到達値は、候補のポインター操作群で実測した方向別の最良値。全連続領域の数学的な最端位置ではなく、版ごとに最良となる操作や到達時の他方の座標が異なる場合がある。同一操作ごとの後退判定は別の回帰調査で扱う。
- 描画端は未変更 PNG の alpha 矩形を、その時点の DOM/CSS 変換で画面へ投影した値。貝殻は本体 PNG に含む。影、発光、現在表示していない表情の全アニメーション軌跡まで画像測定値に含めているわけではない。
- iPhone Safari 実機ではない。ユーザーの実機画像は表示領域・スクロール・比較 iframe の拡大状態などが一致するとは限らず、画像上のラベル値をこの測定値と直接同一視しない。

## 1. 元 PNG の透明余白と足元

Pillow で元 PNG を RGBA に読み、alpha の `getbbox()` を取得した。画像は変更していない。右端・下端は Pillow の排他的上限。

| 画像（128 × 128） | alpha 矩形 `(左,上,右,下)` | alpha 矩形の中心 x | 下端 y |
|---|---|---:|---:|
| `assets/characters/hermit_crab/06.png` | `(10,37,117,120)` | 63.5 | 120 |
| `assets/characters/companions/seal.png` | `(9,19,119,120)` | 64 | 120 |
| `assets/characters/companions/panda.png` | `(11,10,117,120)` | 64 | 120 |
| `assets/characters/partners/gentle_gorilla.png` | `(21,12,107,120)` | 64 | 120 |

alpha が 0 より大きい範囲、16 以上、128 以上のいずれでも、この 4 枚の矩形は同じだった。微小な半透明画素によって外周が過大になっている結果ではない。

再確認用の読み取り処理：

```python
from PIL import Image

paths = [
    'assets/characters/hermit_crab/06.png',
    'assets/characters/companions/seal.png',
]
for path in paths:
    image = Image.open(path).convert('RGBA')
    alpha = image.getchannel('A')
    print(path, image.size, alpha.getbbox())
```

[script.js](../../../script.js) の `dioramaActors()`、調査時点 15354–15365 行は、足元を次の位置に置く。

```text
x = frame.x + frame.w × (alpha.left + alpha.right) / 256
y = frame.y + frame.h × alpha.bottom / 128 + artOffsetY
w = frame.w × (alpha.right - alpha.left) / 128
h = frame.h × (alpha.bottom - alpha.top) / 128
```

つまり、足元 x は本体と貝殻を含む alpha 矩形の横中心、足元 y は alpha 下端。描画矩形の縦中心は足元より半分の高さだけ上にある。縦中心と足元が一致しないこと自体は座標変換の誤りではない。

生成方法は [tools/generate-cast-bounds.py](../../../tools/generate-cast-bounds.py) の `alpha.getbbox()` と正規化処理で確認できる。

## 2. 接触判定とタップ判定は描画矩形とは別

[home-production-model.js](../../../home-production-model.js) の `clearance()` / `separated()`、調査時点 12–13 行は、2 個体の足元差を次の楕円で判定する。

```text
rx = (a.w + b.w) / 2 + 10
ry = (a.h + b.h) × 0.38 + 10
clearance = hypot((a.x - b.x) / rx, (a.y - b.y) / ry)
clearance >= 1 なら接触回避条件を満たす
```

矩形の中心合わせではなく、足元を中心とした論理的な接触距離である。装着物の `extent` はこの式に含まれない。したがって、トイレットペーパーの右側の張り出しが左方向の接触楕円だけを広げる処理はない。

ヤドカリとパンダの組では、半径は native 座標で **118.8622 × 82.1599px**。この条件のカメラ `scaleX=0.6342010144`、`scaleY=1.2814324051` で換算すると **75.3825 × 105.2823 CSS px**。A と D で同じ値だった。これは接触計算の楕円であり、画面上の本体 alpha 矩形と同形であることや、全画素の重なりがなくなることを意味しない。

タップ対象の選択は [home-production-diorama.js](../../../home-production-diorama.js) の `point()` / `hit()`、調査時点 620–631 行。カメラを逆変換した座標で、足元 x を中心として本体の高さだけ上に延びる矩形と実 DOM 対象を確認し、その後に余白付き候補を確認する。この選択用矩形を、経路を止める接触楕円と混同しない。

## 3. 左右の描画保護境界は中央へ戻っている

装着物込みのヤドカリ `extent` は左 **68.78094**、右 **86.75505**、上 **193.42424**、下 **0** native px。本体の幅は **137.56188**、高さ **106.70688** native px。

従来版は [home-production-model.js](../../../home-production-model.js) の `bounds()`、調査時点 6–9 行でこの左右余白に 12px を加え、ステージの左右から差し引く。右側の装着物によって、右方向がより制限されていた。

V3 は [home-production-diorama.js](../../../home-production-diorama.js) の `publishResidentEnvelope()`、調査時点 440–463 行で、本体・表情用余白と装着物を合成する。この条件では `bodySide=ownerHeight×0.55=90.508` が両側の最大値となり、`paintExtent.left=paintExtent.right=90.508` になる。左右共通の保守的な余裕はあるが、左だけに付く余裕ではない。装着物は本体の反転に追従して左右を交換する処理ではなく、兄弟要素として各側の範囲を保持する。

`displayWalkingBounds()`、調査時点 19–43 行は、この描画余裕を深度とカメラに従って画面へ反映してから逆変換する。

| 指標 | 従来版 A | V3 D |
|---|---:|---:|
| native 足元 x の下限 | 80.7809 | 44.8645 |
| native 足元 x の上限 | 259.2449 | 313.1511 |
| 画面上の足元 x の下限 | 132.7027 | 109.9245 |
| 画面上の足元 x の上限 | 245.8848 | 280.0721 |
| 画面上の左右限界の中点 | 189.2937 | **194.9983** |
| 保護フレームの中点 | 194.9983 | **194.9983** |

この描画保護境界では、左へ **22.7782 CSS px**、右へ **34.1873 CSS px** 拡張している。従来の右側余白による偏りがなくなり、V3 はフレーム中央に一致する。V1・V2・V3 のこれらの境界値は同じ。数値だけを実到達の改善量として扱ってはいけない。

確認した足元の画面変換→逆変換の誤差は浮動小数誤差の範囲（例：`5.7e-14`）だった。この条件で大きなカメラ逆変換のずれは確認されなかった。

## 4. 左向き反転で約 1.17px ずれる既存 CSS

[home-diorama.css](../../../home-diorama.css) の調査時点 151 行は、画像の反転原点を `--diorama-origin` にする。

```css
#castStage[data-diorama] [data-diorama-actor]
  .character-visual > :is(.character-asset,.character-emoji-fallback) {
  scale:var(--diorama-facing,1) 1;
  transform-origin:var(--diorama-origin,50% 100%);
}
```

ところが [ui.css](../../../ui.css) の調査時点 83 行には、ID を 2 個持つ、より詳細度の高い指定がある。

```css
#pet #petSprite > .character-visual > .character-asset {
  transform-origin:50% calc(50% - var(--cast-art-offset-y,0px));
}
```

このため、意図した alpha 中心 **49.609375%** の代わりに画像枠中央 **50%** が実際の反転原点になる。ブラウザで A と D の両方の `getComputedStyle()` を確認した結果：

```text
width:             164.547px
transform-origin:  82.2734px 71.9884px   ← 横は画像枠の50%
--diorama-origin:  49.609375% 100%      ← 意図したalpha中心
```

元画像の横中心 64 と alpha 中心 63.5 の差が反転で倍になり、1 source px 分ずれる。画面では `画像幅 / 128 × depth` 程度になる。到達時の描画測定とも一致する。

| 条件 | 描画矩形の中心 x − 足元 x |
|---|---:|
| A、左方向到達時 | +1.1772 CSS px |
| D、左方向到達時 | +1.1686 CSS px |
| D、右方向到達時 | 約 −0.019 CSS px |

これは既存の小さな描画上の不一致として確定した。ただし移動モデルの足元や接触楕円の中心は変わらず、後述の左端では歩行ポリゴン側の制限が残る。今回の経路回帰試作で CSS 原点は変更しない。

## 5. 実到達値と描画端

方向別の最良到達位置。上下では足元 y、左右では足元 x を示す。候補操作群の最良値であり、版ごとに他方の座標が異なる場合がある。

| 配置 | 方向 | 従来版 A | V3 D |
|---|---|---:|---:|
| 4 体 | 左 x | 178.489 | 175.340 |
| 4 体 | 右 x | 245.885 | 280.072 |
| 4 体 | 上 y | 433.741 | 418.140 |
| 4 体 | 下 y | 531.868 | 535.113 |
| ヤドカリだけ・同じカメラ | 左 x | 132.703 | 110.082 |
| ヤドカリだけ・同じカメラ | 右 x | 245.885 | 280.072 |
| ヤドカリだけ・同じカメラ | 上 y | 331.227 | 309.080 |
| ヤドカリだけ・同じカメラ | 下 y | 531.868 | 535.113 |

4 体の左到達時、本体・貝殻の alpha 左端は **116.329 → 113.420 CSS px**。改善は **2.908px** にとどまる。V3 の足元は、描画保護の左下限 109.9245 より **65.42px** 内側にある。

他個体を除きカメラを保持した左到達時、alpha 左端は **75.376 → 52.743 CSS px**。こちらでは描画保護境界の拡張を利用できる。同じ左方向でも、他個体の有無により到達する高さと経路が変わる。

右到達時の alpha 右端は、4 体で **313.193 → 342.929 CSS px**。ただし A の足元 y は約 530、D は約 434 と異なり、既存の深度スケールも異なる。足元の拡大量と画像端の拡大量が一致しないことを、画像の縮小変更と解釈しない。

## 6. 上下の描画余裕

装着ありの上方向余裕 **193.42424 native px** は本体高さ **106.70688px** より大きく、装着物が上限を実際に制約する。4 体時には、その幾何学的上限へ着く前に他個体の接触条件が関わる。上の空白をすべて使えるとはいえない。

V3 の理論上の下限は足元 **535.12349 CSS px**、保護フレーム下端は **545.98352 CSS px**。差 **10.86003px** は、おおむね `下方向描画余裕8 × 深度0.98250 + 追加余裕3` に対応する。実測の **535.113px** との差は目的地への到着許容などの範囲で、追加の大きな空白ではない。

`displayWalkingBounds()` は現在のアニメーションの一瞬に合わせて境界を動かさず、既存の余裕を保持する。76px セリフ領域、Safe Area、下部 UI の保護を削る変更も、この調査では行っていない。さらに下げるには、全対象アニメーションと装着物について、より小さい安全な描画範囲を別途実証する必要がある。

## 確認範囲の限界

この結果は特定のキャラクター段階・装備・配置・画面サイズにおける切り分けであり、全種、全装備、28 体の全配置、全地域、実機 Safari の網羅確認ではない。特に「境界が対称」「候補群の方向別最良値が広い」ことは、同一操作の回帰がない証明にならない。今回の試作では別途確認した経路の回帰を対象とし、この文書で見つけた CSS 原点、背景ポリゴン、カメラ、接触半径は変更しない。
