## 監査と修正

| 経路 | 修正前に再現した問題 | BXの動作 |
| --- | --- | --- |
| バックアップ作成失敗 | 同じtry内の通常セーブまで実行されず、再読込すると進行が古いまま | バックアップが失敗しても通常セーブを試す |
| 主セーブの移行失敗 | JSONとして読めただけで正常バックアップを上書きし、その後の移行と起動が失敗 | 既存の移行処理を最後まで通った候補だけ採用する |
| 復旧後の保存失敗 | 壊れた主セーブをバックアップへコピーして復旧元も失う | 最後に正常に読込／保存できたデータを退避し、書込失敗時も保持 |
| 主セーブが欠落 | バックアップがあっても新しい人生で起動する | バックアップから復旧し、起動直後は主キーを上書きしない |
| 旧版バックアップから復旧 | 通常の移行を通さず、旧年齢や旧ゲームIDが残る | 通常セーブと同じ移行処理を一度適用 |
| 配列などの不正なJSON | 配列を有効なセーブと誤認してバックアップを置換 | トップレベル配列・null・数値・文字列を不採用にして次候補を試す |
| 完全リセット後 | 古いバックアップから消した人生が復活できる | 確定ハンドラーで主キー・バックアップ・メモリ内の退避を消す。他の保存キーは保持 |
| 全候補が読込不可 | 空の復旧候補を非表示・終了時などに保存して原本を消す | 保存を停止して原本を保持。既存の通知欄に保存停止を表示。明示的な完全リセット、または元データの修復後の正常起動で保存を再開 |

保存キーとschemaVersion 4を維持。画像・WORLD_MASTER・CSS・安定ID・通常の進行条件・報酬計算・字幕間隔・ムービーの長さは変更していない。復旧できない場合の保存停止は、正常なデータがないことを空データで隠さないためのもの。バックアップまで壊れたデータの内容を自動修復する機能や、保存領域が使えない端末への永続保存を保証するものではない。

## 検証手順と結果

1. 最初の保存8テストをBWへ適用し、1成功・7失敗。移行失敗では実際の起動時に `endingTiersReached is not iterable` を再現した。
2. 読込候補の移行を修正して5成功・3失敗、書込処理を修正して7成功・1失敗、完全リセットを修正して8成功。
3. 独立レビューで全候補失敗後の原本喪失を指摘され、非表示・終了・連続保存のテストで失敗を再現して修正。最後の正常保存を次回バックアップへ送る境界も確認した。
4. 保存10テストとBWの入力8テストが成功。Node VMは製品の起動・loadState・saveState・doWipe・イベントハンドラーを実行し、保存領域とDOM・時計だけをテスト用に置換。実ユーザーのデータでリセットしていない。
5. `npm test` で既存のruntime・会話・QA fixtureと上記18テストをまとめて検証。旧ウサギ・コアラ・きのこ、v3からv4への年齢変換、旧ゲームID移行と再読込時の二重変換なしを確認。既存の旧PERFECT・作者④⑤の回帰も継続する。
6. 承認済み301画像を開始時mainとバイト比較。個別ハッシュの正本は [BWのマニフェスト](minigame-input-lifecycle-2026-09-10.json)。BXのソースハッシュと照合結果は [BXの検証JSON](post-release-stabilization-2026-09-10.json) に保存。

共通のNodeハーネスを `tests/helpers/runtime-harness.cjs` へ抽出した。抽出直後に既存の入力8テストを再実行して成功を確認してから保存テストを追加。入力8件は実物の共通制御と100本の開始直後の中止を確認する範囲で、100本の手動完走や全canvasドラッグ操作を網羅しない。タッチ入力のブラウザー側の伝播・pointer captureやフレームレートも対象外。
