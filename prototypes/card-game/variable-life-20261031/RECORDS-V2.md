## 2. 移行の手順（正式採用時）
1. 新しいアプリは、まず `naotocchi-card-records-v2` を読みます。
2. それがなければ、`naotocchi-card-records-v1` を**読むだけ**で取り込みます。
   - version 1 の番号は、**凍結した452枚の一覧**（`integration/records-v1-catalog.json`）でIDに戻します。カードが増えても、古い戦績は読めます。
3. 最初の書き込みの時に、次の2つを作ります。
   - version 2（新しい鍵）
   - version 1 の控え：`naotocchi-card-records-v1-legacy`（1回だけ書き、上書きしない）
4. **version 1 の鍵は、書き換えも削除もしません。**
   - 今のアプリを開いても、自分の version 1 をそのまま使えます。
   - 今のアプリは version 2 を読みません（形式が違うと拒否し、誤読しません）。

## 4. 知らないカードIDの扱い（8）
- **version 2 の中の知らないID**（例：新しいアプリが書いた戦績を、古い版が読んだ時）：
  - その対戦だけを `held`（保留）に移し、集計から外します。
  - 書き直しても、**元のまま残します**（失わない）。
  - そのIDを知る版で読むと、元の対戦に戻ります。
- **version 1 の中の範囲外の番号・一覧の違い・version 3 以降：** 今と同じく、ファイル全体を拒否します。
  - エラーを表示し、**何も書きません**。
  - 元のデータは残ったままです（バックアップから戻せます）。

## 5. 対戦の保存（中断・再開）とリプレイ
- 対戦の保存（`records-match.mjs`）は、もともとカードIDの文字列とコマンドの列なので、形式は変えません。
- 新カードの入らない対戦は、統合候補でも main と**完全に同じ**に再生されます。
  - 上の5の fixtures。
  - 公式7デッキの総当たり 560戦で、保存のハッシュが 560/560 一致しました（PLAN-V7 E1）。
- 正式採用時は、ルールの版を **hotseat-9** に上げることを推奨します（`integration/CANDIDATE-V7.md` §5）。
  - 版の一覧と、版ごとの条件（`lover-married.mjs`・`remaining-rules.mjs` の2か所）に hotseat-9 を加えます。
  - 古い保存は、今と同じく元の版で再生されます。
