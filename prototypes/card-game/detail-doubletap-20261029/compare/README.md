# カード拡大の比較モード：右下の白い表示崩れの切り分けと、なめらかさの比較（2026-10-29）

**追記（最終決定）:** 本人の確認で、白い領域の主な原因は「▼ カードの続き」の帯が途中で切れ、右側に本文のクリーム色が見えていたことと考えられます（本人の iPhone で最終確認が必要）。帯は正式版から撤廃し、比較の B（帯なし）は不要になったので削除しました。帯をなくしても白い部分が残る場合に備えて、ほかの比較（色分け・C〜F）は残しています。

前回（HEAD `2ad26474`）の修正後も、本人の iPhone Safari で「拡大時の右下の白い表示崩れ」が残りました。拡大・縮小は以前よりなめらかになりましたが、さらに改善できるかも確かめます。

**この回は正式ゲームのコード（`app.mjs`・`ui-viewport.mjs`・`style.css` など）を変えていません。** 原因が特定できていないため、推測で直すのをやめました。代わりに、本人の iPhone で原因を切り分けられる比較モードを、試遊版にだけ追加しました（`../../detail-stage-20261029/trial.mjs`・`trial.css`・`build-trial.mjs`）。

## Safari での検証ができない理由

- この作業環境には Chromium だけがあり、Safari の描画エンジン（WebKit）がありません。Playwright のブラウザの追加は禁止されています。
- Chromium では、修正前から白い表示崩れは一度も出ていません（[../bottom-right/](../bottom-right/)）。
- 本人限定試遊版は、claude.ai のページの中の枠（iframe）で表示されます。枠の中のページの地は白です。描かれていない部分（穴）があると、白く見える可能性があります。

## カードの構造（白く見えうる部分）

カード詳細の大きなカードは、次の重なりでできています（外側から）。

| 部分 | 見た目 | 色分けでの色 |
|---|---|---|
| ページ（`html`） | 試遊版では claude.ai の枠の中の地。通常は白 | 青 |
| 詳細の画面（`#card-dialog`） | 深緑 | 紫 |
| スクロール枠（`.stage-scroll`） | 深緑。「▼ カードの続き」の帯は最終決定で撤廃 | 緑 |
| カード枠（`.stage-card`） | 透明。中身を `transform: scale` で拡大・縮小 | 水色 |
| カード面（`.card-face`） | 金色の地に**白っぽいグラデーション**。角丸＋はみ出しの切り取り（`overflow:hidden`）、`isolation`、`container-type` | 桃 |
| 枠飾り（`svg.botanical`） | 金の線（面いっぱいの SVG） | （線のまま） |
| 絵（`.card-art`） | 角丸＋切り取り。中に 1152×768 の画像 | 橙 |
| 本文（`.card-copy`） | **クリーム色**（正常なデザイン）。角丸＋切り取り | 黄 |

白く見えうるのは、「カード面の白っぽい地（ほかの部分が描かれていない）」「ページの白い地（穴）」「本文のクリーム色」のいずれかです。

## 比較モード（試遊版の開始画面「カード拡大の比較モード」）

| 選択肢 | 変えること | 白い部分が消えたら、原因は |
|---|---|---|
| A 現行 | なし（いまの正式版と同じ） | — |
| C 切り取りを clip-path に | カード面・絵・本文の角丸の切り取りを `overflow:hidden` から `clip-path` に替える | 角丸の切り取り（WebKit の切り取りの描画） |
| D カードを独立した描画層に | カードを常に別の描画層にする（`will-change: transform`） | 描画層の作り直し・タイルの描き残し |
| E 拡大は実寸（zoom）で描く | 拡大中は `transform: scale` を使わず、CSS `zoom` で実際の大きさに描く | 拡大した変形の描画（WebKit の拡大描画） |
| F 動きなし | 拡大・縮小をすぐ切り替える（0ms） | 動き（アニメーション）とその確定 |

- **色分け**（チェック）は、上のどれとも組み合わせられます。白い部分が何色に変わるかで、どの部分が見えているかが分かります。
- **動きの長さ**は 200ms・260ms（現行）・320ms から選べます。
- 既定（A・260ms・色分けなし）から変えた時だけ、詳細の上部に選んだ条件（例「C・260ms」）が出ます。通常の試遊では出ません。
- 設定は試遊版の中だけに保存されます。正式ゲームには入りません（試遊版の組み立て時だけに加わる部分です）。

Chromium での確認（[variants.json](variants.json)・[screenshots/](screenshots/)）: A・C〜F と色分けのすべてで、ダブルタップの拡大・縮小、元の大きさへの復帰、保存不変、ページ内エラーなしを確かめました（390×844・844×390、14/14）。E でも本文の改行位置は A と同じでした。

## 本人に確かめていただく手順

1. 開始画面の「カード拡大の比較モード」で **A 現行** と **色分け** を選び、「3択の対象指定」の場面を開いて、カメレオンをダブルタップで拡大し、右下までスクロールする。
   - 白い部分が**桃色**に変わる → カード面の地が見えている（枠飾り・絵・本文などが描かれていない）
   - **青**に変わる → ページの地が見えている（その部分がまったく描かれていない「穴」）
   - **黄**に変わる → 本文の背景（その範囲が正しくない）
   - **白のまま** → 上のどれでもない（白い何かが上に描かれている）
2. 色分けを外して、**C・D・E・F** のそれぞれで同じ操作をし、白い部分が出るかどうかを見る。ピンチでの拡大も同じように確かめる。
3. なめらかさは、**A の 200・260・320ms** と **D の 260ms** を比べる。

結果（どの選択肢で白い部分が消えたか、色分けで何色になったか）を教えていただければ、その原因に合わせて正式版を直します。

## なめらかさの調査

拡大・縮小の動きの中で、時間のかかるコマを調べました。CPU を4倍遅くした Chromium で、10回の拡大・縮小のフレーム間隔を記録しています（[frames-result.txt](frames-result.txt)、[frames.mjs](frames.mjs)）。iPhone の値ではありません。

- 2回目のタップの直後（動き出し）に、1コマだけ長いコマがあります（4倍遅延で 40〜60ms、実機の速さならおよそ 10〜15ms 相当）。
  - 内訳の半分ほど（4倍遅延で 11〜30ms）は、行き先の大きさ・位置を測る処理です（一時的にレイアウトを変えて測り、元に戻す）。
  - 残りは、カードを動かすための描画層を作る処理です。
- 動きの途中は 16〜17ms（毎秒60コマ）でそろっています。
- 動き終わり（大きさの確定と描き直し）は 25ms 前後のコマが1つです。
- D（独立した描画層）は、動き出しの層の作り直しをなくす方法です。Chromium では A との差は誤差の範囲でした（拡大 41ms 対 47ms、縮小は同じ 31ms）。Safari は描画層の作り直しの負担が大きいため、実機では差が出る可能性があります。
- E（実寸で描く）は、拡大中に毎回レイアウトを計算し直すため、Chromium では A より重くなりました（拡大 56ms）。

**判断:** 動きの途中はすでに毎秒60コマで、残る引っかかりは「動き出しの1コマ」と「確定の1コマ」です。どちらも、拡大した姿を新しい大きさでくっきり描くために必要な処理で、時間を延ばしても減りません。D で動き出しの1コマが軽くなるかを、本人の iPhone で比べていただくのが確実です。Chromium だけの測定で正式版を変えるのは控えました。
