# 保存互換性と影響範囲（設計案のみ・何も変更していない）

基準：main `953b9c34`（新規対戦の版は `hotseat-5`）。正式保存形式・エンジン・カードは今回変更していません。

## 1. 保存の仕組み（現状の確認）

- 保存は `{version, seed, decks, commands}` だけです（`engine.mjs` `save`）。読み込み時は、その版のエンジンで操作列を最初から再生します（`restore`）。状態そのものは保存しません。
- 版は `RULE_VERSIONS`（`hotseat-2`〜`hotseat-5`）で、ルールが変わるたびに版を上げ、旧保存は旧版の挙動で再生してきました（#449・#452・#473 と同じ方法）。
- 開いている PR #478（かえる、未マージ）が `hotseat-6` を使う予定です。B・C を採用する場合はその次の番号（`hotseat-7` 想定）になります。

## 3. 保存互換の設計案（採用時）

1. 新しい版（例 `hotseat-7`）を作り、別れの値（B）または新カード（C）をその版だけで有効にする。
2. `hotseat-2`〜`6` の保存は、その版の挙動（−10）のまま再生する。保存を新しい版へ変換しない（現在の方針どおり）。
3. 確認：旧保存の実例と旧版の小規模CPU対戦で、操作列・最終状態が変わらないこと。B では「別れを含む旧保存」を必ず含める（現在の旧保存の実例に別れがあるかは要確認。今回の実験では、別れを含む hotseat-5 の対戦記録を `runs/` に多数保存した）。
4. C では、新カードを含む保存を旧版として読ませると拒否されることを確認する（未対応カードとして `validateDeck` が拒否）。

## 4. 今回の実験での扱い

- 写し（`build/`）の B・C・C2・Cx は、版の文字列を `hotseat-5+exp-…` に変えて、正式の保存と混ざらないようにした。
- A の写しは版も挙動も正式と同じで、同じ試合を正式エンジンと写しで行い、保存hashと結果が一致した（`results/equivalence.json`）。
