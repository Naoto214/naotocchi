# 住民を選ぶ・移動させる

全13地域と5段階の倍率について、表示直後と自律移動後のタップ・経路の結果を[画面幅・人数別の集計](interaction-results.md)にまとめた。

全幅・全地域の28体では、最適化+5%で本人に届く点が開始時4,178、8秒後4,135、30秒後4,040（各4,368点）だった。基準は順に4,049、4,044、4,004。+20%では4,055、4,006、3,940だった。4体でも最適化+5%の開始時510/624点が、+20%では459/624点になった。どちらの人数でも拡大幅の決定には移動後の結果を含めたい。

同じ配置に対し12 CSS px先の4方向へドラッグした場合、V5が何らかの経路を提示した数は、森で主人公3/4・恋人3/4・仲間0/4、みずべで3/4・4/4・4/4、都会で2/4・0/4・2/4、家で4/4・4/4・4/4だった。森の主人公では指示した点の1 CSS px以内まで進める経路は1/4だった。V5は行けない方向を検出すると、近くの歩ける地点に振り替えることがある。[経路終点と指示先の距離](evidence/input-planner-fixed-320.json)

## 実際のポインター入力

性能試験でも、見えている住民に実際に触れた際のIDを記録した。320pxの森と390pxのみずべ、各28体・全5倍率の固定配置では、Linux Chromium・Linux WebKitともにタップ20/20、ドラッグを始めた瞬間の選択19/20が狙った住民と一致した。最適化配置ではタップが両エンジン20/20、ドラッグ開始の選択がChromium 19/20、WebKit 20/20だった。事前に見える点を探して押しているため、この数値と全住民3点の成功数は別々に比較する。[タップとドラッグ開始の照合](evidence/input-presses.json)

Linux WebKit 26.5の390pxのみずべ・固定+20%では、森のクマ、柴犬、主人公の3タップはいずれも本人を選択した。主人公に任意方向を指示した最初のドラッグはマーカーが出ても移動しなかった。歩ける方向に指示した追加のドラッグではV5が経路を受理し、主人公の足が9.22モデル座標動いた。[WebKitの操作ログ](evidence/input-pointer-webkit.json)

同じWebKitで320pxの森・最適化+20%を操作すると、恋人を狙った1回が主人公に入り、3役のうち2役を選べた。Chromiumの同ケースでは3/3だった。WebKitの主人公はドラッグで8.97モデル座標移動した。Chromiumでは3タップを続けた直後のドラッグ2回が受理されなかったが、再生直後に同じ方向へ指示すると45.50移動して到着した。430pxの家でも、再生直後のドラッグで23.80移動した。[320pxの連続入力](evidence/input-pointer-320.json) ／ [375・430pxの連続入力](evidence/input-pointer-tall.json) ／ [再生直後のドラッグ](evidence/input-first-drag.json)

別の連続操作では正式な仲間の誘い「**あそぶ!／またこんど**」が開き、背後の住民へのタップとドラッグが止まった。ネイティブ判定で招待表示を特定し、タブが表示中で比較画面も再生中だったことを確認した。「またこんど」（222×36 CSS px）を実際にタップすると招待が閉じ、主人公の返答の動き「bounce」に移った。返答が終わると入力が再開し、主人公のドラッグをV5が受理して足が80.93モデル単位動いた。再生直後に同じ右方向を指示した別の試行でも、固定で23.62、新配置で41.07モデル単位の実移動を確認した。[実タップ](evidence/input-city-four-taps.json) ／ [表示中の誘い](evidence/input-city-four-gates.json) ／ [返答中の画面](evidence/input-city-four-recover.json) ／ [返答後の実移動](evidence/input-city-four-after-reaction.json) ／ [再生直後の実移動](evidence/input-city-four-ready-drag.json)

## 測定方法

比較の単位は画面幅・地域・人数・配置・追加倍率・観測時点。画面幅は320・375・390・430 CSS px、人数は1・4・10・20・28体とした。画面下のゲーム部分の高さから、比較ページの52pxの操作バーを除いた。実機iPhoneの指による遮蔽、熱、Safariのタッチ判定は未測定。

- **タップの分母**は表示している住民1体につき3点。元画像の不透明な絵（アルファ200/255以上）のうち、上部中央・中央左・中央右に最も近い画素を選んだ。ブラウザーの重なり順・座標変換と正式なタップ処理を通して、狙った住民IDが返った点を数えた。この測定は比較の時計を止めたフレームの座標で公式の命中判定を直接読み、住民を実際には選択しない。招待ダイアログや反応中の待機を含む連続タップは別途実ポインターで確認した。奥の人が手前の人に隠れてその人を選べない場合も分母に含む。3点とも届かなかった住民の数を別に記録した。
- **近くへ直進できる方向の分母**は、主人公・恋人・代表の仲間それぞれで8方向、2距離。足から4、12 CSS pxの位置で、V5の歩行境界・地面・実際の前景・他住民との接触・直線全体の安全を調べた。開始時に一部重なっている住民が少しずつ離れられるケースや、迂回による行き先はこの数に含めない。代表の仲間はその世帯の一覧で先頭の仲間。
- **V5の経路受理率**では別に、各住民の足から上下左右12 CSS pxの4点を試した。実行時の `move()` の経路を決める部分を、同じシーン・住民・目的地で副作用なく呼ぶ。元の参照経路、迂回、歩ける近傍への振替も評価し、受理の有無に加えて指示先と経路終点との画面上の差を記録した。試行前後で28体の足の位置・モデル寸法・活動状態・目的地・経路が一致することを照合した。
- **端末入力の再現**では本人用画面を再生し、3役それぞれの不透明な上中央の点をタップした。タップ直後の選択IDと、正式なタップ通知を別々に記録した。短時間で同じ住民に触れると、通知だけが抑制されることがある。ドラッグは主人公の足から右へ12 CSS pxの点をまず試し、狙った住民の経路が受理されてその足が実際に移動した例を記録した。必要に応じてV5が許す近傍への追加試行を行った。Chromiumはタッチポインター、Linux WebKitはタップとマウスのドラッグを使用した。
- 固定配置で倍率を替える前後は同じ28体の位置・物理寸法・経路を確認した。同じネイティブ初期位置を用いる倍率間では移動判定の測定を共有する。最適化配置でも実際に同じ座標候補を使う条件を明示して、重複した測定を個別の検証回数として数えない。

自律動作の表は正式なモデルで8秒および28体では30秒間進め、1モデル座標以上足が動いた住民、全員の歩行距離、到着・交流・接近イベントを集計した。同じ場所に戻った住民は足の変位では数えず、歩いた距離には含む。

320px・都会・28体・+10%で同じ初期配置を別々に開いた経路試験2回では、固定と最適化でそれぞれ64/84点・59/84点になり、28体の初期状態をまとめたハッシュも異なった。3回目は全28体の足の座標・モデル寸法・経路・活動・カメラも一致し、両方64/84点だった。起動時と表示後の倍率変更を入れ替えた追加10回はすべて64/84点。差の原因は特定できなかった。同じ場面の倍率比較には同じ初期位置を使い、独立に開き直した結果にはこの変動が残る。[最初の2回](evidence/input-same-seats-repeat.json) ／ [起動順・初期座標・倍率を照合した追加試験](evidence/input-startup-order.json)

## 再現

比較用のゲームを起動し、PlaywrightとChromiumを用意する。全設定のタップ・直通出口は同じ画面で見た目の測定と併せて取得する。下記は320pxの例。

```sh
python geometry_collect.py http://127.0.0.1:8303/game/limit.html /tmp/home-fixed --widths 320 --counts 28
python verify_interact_routes.py http://127.0.0.1:8303 --widths 320 --regions forest river_lake city home --out routes.json
python verify_interact_pointer.py http://127.0.0.1:8303 --widths 320 --layouts fixed optimized --extras 0 20 --out touch.json
```
