## 計測方法

Linux WPE WebKit 26.5、390×792 CSS px、DPR 2、森・昼・秋・晴れ、サイズBの線形漸増、28体、seed 214。各版の実ゲームを新しいコンテキストで開き、住民画像をデコードし、同じ乱数とネイティブの地形で住民を初期化した。実時間のフレーム間隔に応じて通常の移動・休息・会話、ゲーム通知と再開が進む。実時間が同じでも住民の選択と次の経路は変わりうる。表示人数は、住民要素の矩形が画面と交差し、表示・可視性・不透明度が有効なことを開始時と終了時に検査した。ほかの住民と重なった部分のタッチ可否は別の入力試験で調べている。実機iPhone Safariでの計測は未実施。

旧V6調査の最長584→784ms、843→990msには、Playwrightの `page.clock.set_system_time` を使った。WPEで検査すると、このAPIは日付に加え `requestAnimationFrame`、`setTimeout`、`performance.now` もPlaywrightの関数に差し替える。V7調査では進む日付にだけ開始時刻の差を加え、フレーム、タイマー、単調時計のネイティブ実装を各版の計測前に照合する。旧値は当時の試験結果として残した。新旧の絶対値には計測方法の差がある。[旧計測の全結果](../home-drag-v6/PERF.md) · [WPEでの各関数の確認](evidence/performance-clock-provenance.json) · [旧タイマーを使った初回の制御試験](evidence/performance-baseline-trace.json)

## 確認したDOM測定と修正

住民前景を描くとき、`.home-living-world` の矩形を取得する `presentationRect` が、直前に測ったDOM矩形を使わず、すでにあるカメラの `presentation.world` を返していた。V7ではこの既存分岐をDOM測定より先に実行する。カメラの値、個々の住民や画像の実測値、マスク・遮蔽の座標変換、入力判定の処理は元の関数を使う。

同じV6ランタイムにこの2行の変更だけを当てた試行で、前景描画1回あたりの矩形読取は **2.0357→1.0357回**。元の版の2,856描画すべてにあった前景用のワールド矩形読み取りが、変更後の6,384描画で0回になった。両版とも最初の28体の全座標・役割倍率が同じ。比較時はほかのブラウザー検証も動いていたため、フレーム最大値の差をこの変更単独の効果とは扱っていない。[矩形の読取回数と全フレーム](evidence/performance-world-read-pair.json) · [対応する分岐の単体試験](performance.test.cjs)

実ブラウザーでも元の関数と変更後の関数を同じ要素・同じ時点で評価した。森の縦・横、川・湖、砂漠、森へ戻る5条件で **323,569回すべての矩形の数値が一致**。既存のカメラ矩形そのものを返す31,373回についてはオブジェクトの同一性も一致した。森と川・湖では前景マスクが有効になっている画像も含む。各状態で住民は28体のまま。[実ブラウザーの検査・画面寸法・マスク・ヒット対象](evidence/performance-geometry.json)

## 診断画面の計測

各版の通常比較では診断集計を無効にする。最終V7モデル `dd0789888f19` を使う別の12秒試行で、有効→無効の順に、同じ初期座標でオブザーバーの各メソッドを直接計時した。無効時は0回・0ms、有効時は354回、記録時間の合計23ms（フレーム処理95回・7ms、モデルステップ処理176回・11msを含む）。両方で開始・終了時とも28体が画面にいた。同居ブラウザーがある時間帯の全フレームp95は無効1,288ms・有効252ms、p99は3,080ms・1,048ms、最大3,080ms・1,211msだった。全フレームは負荷の変動も受けており、診断による高速化を示す数値には使えない。外側の設定画面を開いたときの1Hzのパネル再描画は計時対象外。最初の制御試験はモデルのオブザーバーを再接続しておらず、コントローラー費用だけを計測していたため、この値から除いた。[最終版の全診断メソッドの時間・フレーム・指紋](evidence/performance-diagnostics-cost.json) · [コントローラーのみの制御試験](evidence/performance-frame-hooks-control.json)

## モデル・描画・Linuxの切り分け

負荷が重なる時間帯の別試行で、ネイティブのモデルステップ、経路、接触述語、道譲り、住民DOM、環境描画、カメラ更新、スケジュールされたコールバックを観測した。メインスレッドと独立のWorkerは20ms周期で時刻を記録した。Linuxの `/proc/.../schedstat` から、実際にCPUを使った時間と実行可能なのに待った時間を取り、cgroupのCPU制限とWebKitソフトウェア合成スレッドの実行時間を併記した。コールバック時間は入れ子を含む経過時間で、CPU時間と単純に足せない。

## 再現

実ゲームを比較版のビルダーで配信し、このディレクトリから以下を実行する。Linux版Playwright WPE WebKit 26.5を使用した。実行ファイルが標準のPlaywrightインストール先にある場合は `WEBKIT_PATH` を省略できる。負荷を調べる追加の処理は、通常のフレーム計測と別の試行で有効にする。

```sh
export WEBKIT_PATH=/workspace/work/qa-browsers/webkit-2336/pw_run.sh
final_model=dd0789888f19c57f1a88b05e144c98d82a77b57b7d04dd18e55e84dcd8ea4baf
python performance-clock.py --arms v5,v6,v7 --seconds 180 --quiet --expect-v7 "$final_model" --out /tmp/mobility-forward.json
python performance-clock.py --arms v7,v6,v5 --seconds 180 --quiet --expect-v7 "$final_model" --out /tmp/mobility-reverse.json
python performance-clock.py --arms v5,v6,v7 --seconds 16 --trace --expect-v7 "$final_model" --out /tmp/mobility-trace.json
python performance-clock.py --arms v7+,v7 --seconds 12 --hud-cost --expect-v7 "$final_model" --out /tmp/mobility-diagnostics.json
node --test performance.test.cjs
```

上記に加え、ゲーム配信ディレクトリと13地域分の検証アーティファクトを展開したディレクトリを指定して、モデル単体の再生と入力集計を再現できる。

```sh
node performance-helper.mjs /path/to/game /tmp/helper-forward.json
node performance-helper.mjs /path/to/game /tmp/helper-reverse.json --reverse
python performance-input.py /path/to/extracted/regions --model-sha256 "$final_model" --out /tmp/drag-cost.json
python performance-summary.py /tmp/mobility-forward.json --out /tmp/frame-attribution.json
```
