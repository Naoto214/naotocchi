# 海・森の実画面検証

比較の対象は海の夏・晴れ・夕方と森の夏・晴れ・昼。強度100%、通常速度、同じ保存フィクスチャを使った。実ホームの結果と元絵に対する背景合成だけの結果を区別している。

共有Linuxホストの短時間負荷行列（390×844 CSS px・DPR 2）はCPU 2・3、別の10分間診断はCPU 0・1に固定した。追加の連続観察はCPU 4。メモリー・システム全体のCPU枠は共有し、各条件は1回の測定。Linux WPEとChromiumはそれぞれ同一エンジン内で比較する。4体以上では背景キャッシュの時刻区分が55msから120msになるため、住民を増やしたときにrAFが上がる組み合わせもある。微小な差の順位は参考値とする。28体の長時間試験は別途、住民更新・描画・既存UI処理を分けて計測した。[10分間の診断](HITCHES.md)

2026-11-19 UTCで、初回180秒観察は06:20:29～06:24:54、演出時計180秒の再試験は06:26:39～06:31:24。6秒ずつの主負荷行列はChromiumが06:25:32～06:30:17、WebKitが06:31:33～06:40:01に実施した。海4体E2の入力再試験（CPU 4）は06:37:54～06:39:09、主行列と同じCPU割当の再試験は06:40:02～06:40:54。

海の描画器は試験中に `832f1e0f` から `449faf76` へ更新された。ソース差は100%超～200%未満の強度の補間式1か所で、0・50・100・200%の係数は一致する。連続観察と短時間負荷はすべて100%。森は `3107cfa3`。

## 環境条件とアクセシビリティ

Linux WebKit 26.5 の Canvas で、各地域の4枚の時間帯原画に実際の描画関数を適用した。2地域 × 4案 × 4時間帯 × 4季節 × 4天気の512通りが描画できた。160×240画素で RGB のいずれかが4階調以上変わる画素を数えた。

- 32組の地域・案・時間帯すべてで、強度0の原画との差は0画素。100%と200%には各組で可視差が出た。
- 「動きを減らす」では、描画器へ23.25秒と57秒を明示的に渡しても32組すべてで差は0画素。住民の自律判断、機器の表示リフレッシュ、原画自体の時間帯切替を含まない測定。
- 海E3の季節単独の差は、時間帯ごとに最大64～105画素。天気単独では最大5,878～8,074画素。森E3は季節184～2,353画素、天気1,661～2,597画素。比較時刻23.25秒における晴天・夏との条件別差で、該当物のある部分にだけ季節が出る。

## 30秒・60秒・180秒の連続観察

8つの実ホームを初期化してから、一度だけ各演出時計を0に戻し、実時間180秒までシークせず継続再生した。条件間でCPUを共有したため、この試行は性能比較には使わない。ブラウザーは320×844 CSS px、住民1体。図の列は左からD3・E1・E2・E3、行は30・60・180秒。実画面では住民を含み、背景図では住民の影響を除いた。連続試験の4列は別々に動くので、時刻ごとの住民位置には差が出る。同じ瞬間の住民位置を共通にした比較には分割表示を使う。

| 地域 | 案 | 30秒 | 60秒 | 180秒 | 180秒時の演出時計 |
|---|---|---:|---:|---:|---:|
| 海 | D3 | 18.6% | 19.5% | 0.0% | 72.48秒 |
| 海 | E1 | 29.5% | 29.0% | 0.0% | 163.44秒 |
| 海 | E2 | 25.3% | 10.4% | 0.0% | 85.20秒 |
| 海 | E3 | 28.5% | 23.7% | 0.0% | 93.08秒 |
| 森 | D3 | 9.6% | 4.3% | 0.0% | 167.91秒 |
| 森 | E1 | 9.7% | 20.0% | 0.0% | 178.39秒 |
| 森 | E2 | 9.9% | 22.7% | 0.0% | 110.68秒 |
| 森 | E3 | 13.4% | 12.8% | 10.2% | 178.13秒 |

数値は各時点の直前約0.5秒（実測0.13～0.98秒）に背景Canvasを208px幅に縮小して読み、RGBの最大差が4階調以上だった画素の割合。割合は動きの面積と変化の速さ両方に影響されるため、美しさの得点には換算しない。

180秒の時点では7画面で本来の「なかまの さそい」が開き、住民と背景時計が待機した。「またこんど」を押すまでの停止もここには含めている。森E3の画面はこの時点で動作中だった。

### 「またこんど」で戻った後の180秒

静置試験とは別に、ゲーム本来の誘いが出たときだけ「またこんど」を押し、各案の演出時計が180秒に達するまで実ホームを再生した。各ボタン操作は時刻とともに記録。開始時以外のシーク、強制タイマー更新、住民の座標操作はしていない。

| 地域 | 案 | 演出30秒の変化面積 | 60秒 | 180秒 | 経過実時間 | 誘いを閉じた回数 |
|---|---|---:|---:|---:|---:|---:|
| 海 | D3 | 19.0% | 18.1% | 17.8% | 183.4秒 | 1 |
| 海 | E1 | 30.6% | 22.8% | 31.2% | 182.2秒 | 1 |
| 海 | E2 | 24.7% | 24.5% | 25.0% | 181.5秒 | 1 |
| 海 | E3 | 31.8% | 33.6% | 29.0% | 182.9秒 | 1 |
| 森 | D3 | 12.1% | 8.9% | 7.9% | 184.3秒 | 1 |
| 森 | E1 | 7.7% | 16.0% | 10.3% | 185.0秒 | 1 |
| 森 | E2 | 10.9% | 21.9% | 11.1% | 182.2秒 | 1 |
| 森 | E3 | 13.4% | 21.2% | 12.5% | 182.5秒 | 1 |

海は30秒でE1/E3の波の面積がD3より広く、60秒・180秒でも海面が動き続けた。夕日の反射の軸と浜の色を維持している。森のE3は60秒の風で変化面積が上がり、180秒では落ち着いた。常に同じ強さで樹冠が動く見え方にはなっていない。いずれも180秒時点で住民の顔・既存UIを視認できた。

森では住民が奥へ進むと、林床より上の樹冠の手前に浮いたように見える配置が残る。海でも深い水に見える位置へ進む場面がある。背景の変形と足元の演出だけでは、既存の移動範囲と原画上の歩ける場所の差は埋まらない。本人が180秒以上眺めた際の好みや疲労感は未評価。

## 比較操作・保存・画面幅

Linux WebKit 26.5 で8件の地域・幅の組み合わせを確認。320・375・390・430pxの海と森で、D3→E1→E2→E3の切替、分割境界5%・95%、強度0・150・200%、地域別の個別チェック（海10、森11）を操作した。各スイッチを外すとゲーム内の設定も同期した。4体のID・座標・スケールは切替前後で全件一致し、保存キーの検査値を保持した。背景のCSS描画矩形と演出矩形の最大差は0.010px。

## Chromium の短時間負荷

各セルはホームコントローラーの内部更新Hz／キャッシュ済み背景をCanvasへ転送した回数毎秒／requestAnimationFrameのコールバックHz。内部値は起動直後から最大300回の更新間隔を平均し、ゲームが15回ごとに公開した最新値。後二つの値は各画面の6秒の観測窓で数えた。rAFは表示完了を保証しない。条件ごとに新規コンテキストを起動し、1画面の測定後に住民をドラッグした。

|---|---:|---:|---:|---:|---:|
| 海 | 1 | 26.0 / 16.9 / 53.0 | 27.1 / 17.6 / 57.2 | 27.1 / 17.8 / 57.0 | 26.6 / 17.8 / 57.5 |
| 海 | 4 | 24.7 / 7.7 / 52.0 | 20.0 / 7.3 / 46.8 | 21.1 / 7.5 / 50.5 | 22.3 / 7.7 / 50.4 |
| 海 | 28 | 20.7 / 8.2 / 53.4 | 18.6 / 7.2 / 43.2 | 19.9 / 8.3 / 54.4 | 19.5 / 7.5 / 48.5 |

| 森 | 4 | 24.3 / 7.9 / 53.7 | 24.6 / 8.2 / 54.8 | 25.2 / 8.3 / 54.5 | 24.9 / 8.1 / 54.4 |

ドラッグ目標の表示は24/24件。CDPのタッチ列で、pointermoveの時刻から次のrAFまでの全240件の中央値39.8ms、最大464.2ms。ドラッグ終了から次の描画を物理計測した値とは区別する。通常観測窓のrAF間隔p95は16.7～16.8ms、単発最大866.6ms（forest/28/E3）。

## Linux WebKit の短時間負荷

各セルはホームコントローラーの内部更新Hz／キャッシュ済み背景をCanvasへ転送した回数毎秒／requestAnimationFrameのコールバックHz。内部値は起動直後から最大300回の更新間隔を平均し、ゲームが15回ごとに公開した最新値。後二つの値は各画面の6秒の観測窓で数えた。rAFは表示完了を保証しない。条件ごとに新規コンテキストを起動し、1画面の測定後に住民をドラッグした。

| 地域 | 住民 | D3 | E1 | E2 | E3 |
|---|---:|---:|---:|---:|---:|
| 海 | 1 | 4.8 / 11.3 / 11.1 | 6.2 / 11.7 / 11.7 | 6.9 / 10.7 / 10.6 | 5.2 / 8.9 / 8.8 |
| 海 | 4 | 8.4 / 7.6 / 18.8 | 7.0 / 7.2 / 13.7 | 3.0 / 4.7 / 6.4 | 7.6 / 7.3 / 15.8 |
| 海 | 28 | 5.9 / 7.7 / 18.4 | 5.6 / 8.0 / 29.2 | 6.2 / 7.5 / 20.8 | 6.3 / 7.5 / 20.0 |
| 森 | 1 | 8.2 / 13.9 / 15.4 | 8.4 / 12.9 / 15.2 | 7.1 / 12.8 / 13.4 | 6.0 / 10.7 / 11.7 |
| 森 | 4 | 8.1 / 7.6 / 19.2 | 9.4 / 7.5 / 24.9 | 4.1 / 6.0 / 9.4 | 8.2 / 7.7 / 17.3 |
| 森 | 28 | 6.9 / 8.0 / 29.1 | 7.2 / 6.0 / 26.1 | 5.0 / 4.9 / 14.7 | 5.7 / 4.9 / 17.3 |

ドラッグ目標の表示は23/24件。Playwrightのマウス入力で、pointermoveの時刻から次のrAFまでの全235件の中央値198.0ms、最大685.0ms。ドラッグ終了から次の描画を物理計測した値とは区別する。通常観測窓のrAF間隔p95は88.0～408.0ms、単発最大1504.0ms（forest/28/E3）。

海4体E2の初回は目標マーカーを確認できず、rAFは6.4Hz。同じフィクスチャを使うCPU 4（1コア）の独立3回では、3回ともカーソルが住民に届き、目標マーカーを表示した。rAFは順に6.6／5.7／6.5Hz。初回の入力未確認を速度やエフェクトだけに帰する根拠は得ていない。D3でもLinux WPEの画面では遅延があり、この環境での値をiPhoneの値へ換算できない。

[CPU 4での独立再試験](evidence/drag-webkit.json)

主行列と同じCPU 2・3への割当でも海4体E2を3回追加測定した。rAFは25.6／26.5／24.7Hz、目標マーカーは3/3件。初回の6.4Hzはこの再試験で再現せず、同じCPU割当でも測定時刻・同時稼働の違いにより結果に振れがある。E2固有の恒常的な負荷とは判定できない。

## 環境の切替

住民4体で夏・晴れの海夕／森昼から冬・雪・夜へ変更。D3と各E案の全8件で背景合成アルファは単調に1.0へ達し、最初に検出した半透明フレームから全切替まで3.98～4.05秒。これは描画時点をサンプリングした値で、設定4秒のタイマーを直接計測した値とは異なる。

[切替中の各フレーム・更新値](evidence/switch-chromium.json)

## 再現方法

ローカルの比較ビルドを用意し、Python の Playwright・Pillow と Chromium または Playwright Linux WebKit を用意する。

```sh
python verify_v4.py http://127.0.0.1:8194 duration
python verify_v4.py http://127.0.0.1:8194 active
python verify_v4.py http://127.0.0.1:8194 ui --engine webkit
python verify_v4.py http://127.0.0.1:8194 conditions --engine webkit
python verify_v4.py http://127.0.0.1:8194 matrix
python verify_v4.py http://127.0.0.1:8194 matrix --engine webkit
python verify_v4.py http://127.0.0.1:8194 drag --engine webkit --drag-case sea/4/E2
python verify_v4.py http://127.0.0.1:8194 switch
python verify_v4.py http://127.0.0.1:8194 speed --engine webkit
```

Linux WebKit のiPhone相当幅は、タッチ対応・DPR 2のLinuxブラウザーを用いた。iPhone Safari実機のタッチ遅延、パネルへの表示完了、発熱、電池消費は未検証。
