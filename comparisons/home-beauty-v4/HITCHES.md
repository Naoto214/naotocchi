## E3の最大停止と演出の追加負荷

開始241.9秒後に到着間隔が **3872.3ms** まで伸びた。うち **3781.8ms（97.7%）** が `model.step` 1回と重なる。背景描画は1.7ms、その中の環境合成は1.1ms、海のE3描画は0.9ms。住民のDOM反映は38.2msだった。前面表示・28体・一時停止なしで会話中に発生し、Long Taskと3828.0ms重なった。CPUサンプル391件のうち `getBoundingClientRect` が82、歩行判定 `walkable` が38、経路グラフ `buildEdges` が22、GCが15件だった。[E3の記録](evidence/hitches-e3.json)

環境合成はD3で4389回、E3で4516回。1回の平均負荷は約0.58ms増え、単発の最長値も45.3msから90.3msになった。E3の海面描画にはフレーム予算を超える呼び出しがある。両案の秒単位の最長停止は住民更新と一致する。各案1回の試験で、D3は31回の定点確認のうち8回、E3は10回が会話の選択待ちだった。世話の実行回数もD3が6操作、E3が3操作だったため、平均rAF頻度や停止回数の差を演出単独の改善量とすることはできない。

両案とも全定点で28体、終始前面表示、ページ例外0件。全3回のドラッグで対象の住民に実際のタッチイベントを送信した。D3側で使用した既存描画器・モデル・コントローラー等の計測対象7ファイルのハッシュはE3側と一致する。海のE描画器はD3試験後に最終版へ更新され、E3の試験には最終版（`449faf76`）を使用した。D3中のE描画関数の呼び出しは0回。現行V5の住民更新や衝突判定は比較の中で変更していない。

## D3で再現した秒単位の停止

開始187.7秒後、画面が前面にあり、28体の住民がいて、会話吹き出しが出ている場面で、rAFコールバックの到着が **3759.6ms** 空いた。この間の `model.step` 1回が **3636.1ms（96.7%）** を占めた。背景描画は0.7ms、住民のDOM反映は41.2ms。Chromiumでも同じ区間に重なるLong Tasksを計3758.0ms記録した。CPUサンプル460件のうち、106件が `getBoundingClientRect`、46件が歩行可能領域の `walkable`、31件が経路グラフの `buildEdges`、16件がGCだった。305.7秒の別の2312.7msの停止も、2128.2msが住民更新だった。

一方、開始320秒の食事操作では到着間隔が1320.4msになり、うち1210.7msが本編の `render` と重なった。ブラウザーは同じ `feedBtn.onclick` の強制スタイル・レイアウトに1102.6msを記録した。操作時のレイアウト負荷は、住民の経路探索とは別の改善候補となる。

VERSION 3に残る最大値2849.8msについては、該当する20秒窓に残っていた最長タスク210msと停止の時刻が異なる。今回の同期した関数計時で原因を絞れたのは、今回観測した停止である。[V3の観測データ](https://github.com/Naoto214/naotocchi/blob/5363cd8fefa15f8aed93fc403203198d295ac923/comparisons/home-beauty-v3/evidence/v3-endurance.json)・[今回のD3記録](evidence/hitches-d3.json)

経路探索は歩ける範囲、画面で見える位置、他の住民との衝突を繰り返し確認する。次の個別試験では、同じモデル更新内の `getBoundingClientRect` の呼び出し元と、経路グラフを再構築した回数を記録すると、同じ判断を繰り返す箇所を絞れる。食事操作ではDOMを更新した直後に位置を読む回数を別に計る。移動V5、衝突判定、ゲームUIの変更はこの比較の対象外とした。

## 試験条件

夏の夕方・雨の「うみ」、28体、演出強度1、通常速度、390 × 844 CSS px、DPR 2。各案を別のブラウザープロセスで600秒ずつ前面表示した。住民とゲームの乱数の初期シードはいずれも214。0秒・180秒・400秒に画面上の住民へタッチドラッグを送り、20秒ごとに同じ基準で食事・清掃・薬・起床の世話を行う。シードは共通でも、実際の入力時刻や住民更新の回数がずれると、以降の会話や位置は分岐しうる。

Linux版Chromiumのメインスレッドをプロファイルした。ブラウザーと計測プロセスはCPU 0・1で実行した。同じホストでは別の検証も動いており、計測用CPUの指定で分離しても、ホストの共有負荷や実行時刻による差は残る。iPhone実機のリフレッシュレート、GPUが描いたフレームの実際の表示時刻、熱、電池消費はこの試験の計測対象外。

## 計測方法

- ブラウザーがrAFコールバックへ渡した時刻の差と、コールバックの実行開始を `performance.now()` で読んだ時刻の差を別々に保存する。表中の「到着間隔」は後者。いずれかが約250ms以上なら状態を記録し、最大の12区間には詳細を残す。
- Playwrightのローカル応答内で正式ホームの住民更新 `model.step`、背景 `world.draw`、住民のDOM反映 `paint`、同期、タッチ、正式ホームのゲームループと描画を計時する。比較用の環境合成 `composeNature` とD3/E3の描画関数も個別に計時する。配信用ファイルは書き換えない。JSONにある各ファイルのSHA-256は計測処理を加える前の応答内容を指す。
- 発生区間と関数の開始・終了が重なった時間を計算する。0.4ms未満の呼び出しは全体集計に含み、区間の内訳から省く。`world.draw` に `composeNature` が含まれ、コントローラーの `frame` に住民更新と描画が含まれるため、表の各列は加算できない。
- 同時刻のChromium Long Tasks、Long Animation Frames、強制レイアウト時間、約8ms間隔のV8 CPUサンプルを照合する。GCは実際にガベージコレクターが採取されたサンプル数で示す。GC停止の正確な所要時間は得られない。タブの可視性、ゲームの一時停止、会話、選択肢、住民数も記録する。
- 計測器自身にも負荷がある。画面の滑らかさや案間の速度差には、計測用関数を挿入しない短時間比較も併用する。関数の完了はCPU側の完了であり、GPUで描画が完了した時刻を示すものではない。

ローカルでの再現には比較ページのビルド、Python Playwright、`/usr/bin/chromium` が必要。

```sh
taskset -c 0,1 python comparisons/home-beauty-v4/verify_hitches.py http://127.0.0.1:8194 D3 /tmp/hitches-d3.json
taskset -c 0,1 python comparisons/home-beauty-v4/verify_hitches.py http://127.0.0.1:8194 E3 /tmp/hitches-e3.json
```
