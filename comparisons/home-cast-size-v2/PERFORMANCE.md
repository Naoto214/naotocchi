# 28体の配置と処理時間

最終版の28体では、Chromiumの森の最長間隔が269ms、みずべが1.13秒だった。みずべの最長区間でV5住民更新が1.01秒を占めた。森のLinux WebKitは最終版1.84秒で、現行1.20秒、採用サイズ1.43秒より長い。最終版で28体の初期配置候補を作る関数は、森・みずべとも起動中に1回呼ばれ、住民を動かした計測区間では0回だった。長い停止は残っており、条件によっては採用サイズ版より長く待つ場面がある。

森の320 × 568 CSS pxと、従来から長い停止が出ていたみずべの390 × 844 CSS pxで、実際のホームを動かした。現行サイズは#570の通常倍率100／100／100%、採用サイズは同じ#570の120／120／105%、最終調整は採用サイズで初期配置を変更し一覧切替を廃止したもの。全案で秋の晴れ・昼、同じ名簿・装備・落ち葉B・通常速度を使った。各試行は新しいブラウザーページで起動し、地形・カメラ・住民の準備完了後に計測した。初期シードは共通で、実時間の進み方・歩いた経路は試行で異なる。

Linux共用ホストでCPU 0・1に固定し、DPR 2、比較用ヘッダー52pxを差し引いたゲーム領域を実寸で開いた。rAFはブラウザーのコールバック到着頻度。住民更新は制御器が採用した更新回数で、複数のV5ステップを1回に含むことがある。タイマーは試験時の配信応答にだけ挿入した。物理iPhoneでの表示フレーム、指から液晶表示までの遅延、発熱・電力は未測定。

## 接触判定とブラウザー側の描画

別のChromium計測で、森320px・28体を各8秒ずつ動かし、ネイティブの住民間距離判定 clearance の呼出し回数とブラウザーのタイムラインを取得した。計測用カウンターやトレースの負荷が加わるため、この試行の数値は上のフレーム間隔表には含めない。Paint・RasterTaskは各スレッド上の合計。並行実行されるため、体感遅延を求める目的で合算できない。

| 案 | 経路計画 回 | 住民間距離判定 回 | Layout ms | Paint ms | RasterTask ms |

各試行で初期位置・実際に選んだ移動先・実時間ステップの進行が結果に影響する。移動モデルのハッシュとモデル上の体寸は比較用JSONに記録した。[ブラウザートレースと接触判定の件数](evidence/perf-trace.json)

## 再計測

先に#570のビルドを8201、最終調整のビルドを8202でローカル配信し、Python・Playwrightとブラウザーを用意する。ChromiumはCHROMIUM_PATH、WebKitはWEBKIT_PATHまたはPLAYWRIGHT_BROWSERS_PATHを指定できる。

taskset -c 0,1 python verify_performance.py --counts 28 --seconds 40 --inputs 10 --out forest.json
taskset -c 0,1 python verify_performance.py --region river_lake --width 390 --height 844 --counts 28 --seconds 25 --inputs 0 --out river.json
taskset -c 0,1 python verify_performance.py --engine webkit --counts 28 --seconds 12 --inputs 4 --out webkit.json
taskset -c 0,1 python verify_performance.py --counts 1 4 10 20 --seconds 5 --inputs 0 --out counts.json
taskset -c 0,1 python verify_performance.py --counts 28 --seconds 8 --inputs 0 --trace --contacts --out trace.json
