## 指を離した場所と、住民が歩いて着いた場所

森・28体・390pxで各住民の足元を中央へ12 CSS px動かした。V4では拒否された21件すべてが他の住民の接触範囲に入る指定だった。うち19件は出発時点から範囲が重なり、1件は地形でも通れない場所だった。タップとドラッグのしきい値は画面上の8 CSS pxで扱い、指を離したイベントでも移動量を判定する。

短い指示では、元の接触楕円と歩行地形の中で、希望位置に近づける連続した経路を探す。すでに重なっている住民は重なりを増やさず抜け出せる。長い指示では既存の迂回経路を使い、近くに着けるか、途中まででも希望方向に十分進めるかを確かめる。混雑で進めないときは指の方向を向く。通れるようになった場合は、移動V5の期限付きの再試行で歩き出せる。地形の拡張と瞬間移動は使用していない。 [原因・指示処理時間・到達結果](DRAG.md) ／ [タッチ入力の地域別記録](INPUT.md)

同じページで約112秒かけて28件を続けて入力した試験では、27件が本人へ届き、12体が実際に到着した。1件は指がペンギンに当たったものの、既存の跳ねるリアクション中で経路指示が発行されなかった。おうち3体の通常再生では、重なった住民を狙った2件がほかの住民に当たった。初期の密集と前後に重なる絵の選びにくさは本人試遊で確認してほしい。

## 28体の停止と移動V5

同じ地形の辺を何度も判定し、1回の経路要求中に前景と住民の位置を繰り返し測っていた。固定地形の判定を再利用し、動く住民と前景は今の操作の間だけ再利用するようにした。歩行中は、その瞬間にいる住民との接触を各ステップで再確認する。自律行動・道譲り・会話の頻度と参加者数は従来どおり。

最終配布モデルで森430pxとみずべ375pxの28体を、同じ住民・配置・乱数で各10秒間、2種類の乱数で比較した。Linux WebKitでの結果を示す。rAFはブラウザーが次の描画処理を呼んだ間隔から求めた。

| 28体の地域と乱数 | 最長フレーム間隔、V4 → 仕上げ版 | 平均rAF呼出回数/秒、V4 → 仕上げ版 |
|---|---:|---:|
| もり・214 | 956 → 709 ms | 35.2 → 49.4 |
| もり・2903 | 812 → 775 ms | 40.3 → 48.5 |
| みずべ・214 | 1,344 → 791 ms | 44.9 → 51.6 |
| みずべ・2903 | 735 → 748 ms | 46.4 → 50.4 |

同じ森390px・28体を旧版と仕上げ版でそれぞれ3分間、ゲームの時刻も進めて連続再生した。両版とも3つの1分区間で住民が歩き、通常の通知による一時停止は計約7.6秒だった。最長フレーム間隔は**3,707→645ms**、500ms超は**16→1回**、1秒超は**4→0回**、rAFは39.0→55.8回/秒。測定した実時間は182.1→180.0秒、進んだモデル時間は168.2→173.0秒だった。この3分間は同一乱数1組の結果である。実時間再生ではフレームの間隔が変わるため、移動開始は41→28回、会話などのsocialイベントは3→2回になった。同じ時間刻みで比べた行動の一致は下記の1,500ステップで確認した。

冒頭の短時間4条件では、500msを超える間隔は8回から4回に、1秒を超える間隔は1回から0回に減った。みずべの1条件では最大が13ms長くなった。試作途中のおうち4体の対照では3,476→1,929msの停止が残り、ホストが混んだ森28体の別試行では1,840→2,190msに伸びた。おうちでは複数の経路探索を含むモデル更新が長くかかった。別に最終版で行ったCPU 1コア共有・68秒の試験では、V4の2,263msの間隔に2,147msのモデル更新が重なり、そのうち1,792msは経路探索だった。最終版にも1,245msの間隔が1回あり、この区間では計時した50ms以上の単独処理を特定できなかった。住民モデル・経路・住民描画・背景・自然描画の個別時間と全試行を記録した。 [性能の内訳と全条件](PERF.md)
