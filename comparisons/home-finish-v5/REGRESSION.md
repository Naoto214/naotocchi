# 採用したサイズBと既存ホームの回帰検証

## 測定方法

同一のChromiumで、受け入れ済みの比較版V4と仕上げ版を別々のページとして開いた。どちらもゲーム本体で描画した主人公・恋人・仲間を測定する。昼の地域と世帯人数を指定して375px幅で起動し、320・390・430pxに順にリサイズする。各人数の住民名簿はゲームの保存用フィクスチャと照合する。ゲーム高はそれぞれ760・516・792・880 CSS px。端末倍率2、モーション軽減、停止、時計固定、配置はV4のサイズ別配置とした。ネイティブカメラの投影と画面寸法が1秒間安定してから採取した。[ブラウザー検査](regression_grid.py) ／ [実DOMの測定式](regression_probe.js)

各住民について、描画中のCSS変換からカメラの縦横倍率、体格倍率と奥行き倍率を除き、主人公・恋人120%、仲間105%に人数と幅の追加係数を一度だけ掛けた値と比べる。許容差は各軸0.0001、縦横倍率比も1から0.0001以内。ゲーム本来の主人公110%指定も残っていることを検査する。画像は両版で同じ役割、住民ID、URL、デコード後の原寸を要求する。各住民には描画済みの影が1個あり、その位置に対応する地形の足元が有効であることを確かめる。

正常な1〜28体をすべて受理し、空欄・0・負値・29・小数・先頭ゼロ・指数表記・先頭空白は本人用画面の既定28体に戻る。配布したサイズ関数の検査では、300〜430pxの10幅×28人数で役割別の倍率を照合した。サイズCや、19体で一度に拡大する指定が渡っても、Bの1体ごとの増加を維持した。[人数入力の検査](shell.test.mjs) ／ [配布関数の280件](verify_policy.cjs)

仕上げ版では同じ描画時点で接地補正を入・切・入と切り替え、モデル上の足、投影した足、奥行き、画像の描画矩形、表示中のリボン等の装備矩形の厳密一致を検査した。両版の独立した起動／リサイズで同じ時点に到達したことまでは仮定せず、足・画像枠・装備を含む全体のハッシュは双方を個別に記録した。旧84%切り替えボタンのDOMがゲームにないこと、本人用設定にサイズ・倍率・配置の切り替えがないことも検査した。

時間帯の検査は幅375px、19体の本人用画面から朝・昼・夕方・夜を操作する。デコード済みの1024×1536の背景が裏キャンバスに描かれ、同じ画像を含む裏キャンバスが不透明度1で実際に表示中の地形キャンバスへ合成されるまで待つ。各地域で同じ19体、サイズBの追加1.5%を維持していることを照合する。[時間帯の検査](regression_dayparts.py)

## 安全な足位置の保持と復帰

同じ地形試験で、V4と仕上げ版の配布物からそれぞれの移動モデルと経路探索を直接読み込んだ。住民1体を歩かせ、同じ床に新しいナビゲーションを設定すると到着した足はそのまま残った。歩ける床の境界を縮めてその足が無効になった場合は両版とも同じ有効点に復帰し、次の再同期でもそこに留まった。この試験で更新したのは表示モデルの地形であり、保存データの読み込みは別の起動検査で扱う。[両版の座標とコードSHA-256](evidence/native-position-recovery.json) ／ [再現コード](qa/check-position-recovery.cjs)

既存の移動V5の境界・地形・経路の3スイートも対象ソースで再実行し、27件が成功した。既存路線の外縁、細い禁止帯、到達候補の方向、成長時に安全な足のカメラ更新を待つ処理を含む。[実行したテスト名と件数](evidence/movement-base-regression.json) ／ [再構成したネイティブソースでの再現](qa/check-legacy-movement.py)
