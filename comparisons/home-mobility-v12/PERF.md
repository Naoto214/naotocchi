# 28体の移動と描画の処理時間

森28体の実際のホームをLinux WebKit（WPE 26.5）で動かし、V10・V11足元のみ・V12を比較した。通常の描画・入力は390×792 CSS px、DPR 2、乱数214。通常再生は各版を8秒予熱してから180実秒。通常順と逆順は独立の専用ランナーで、各順序の3版は同じランナーを使った。

## 最終試作の観測結果

森28体の通常再生で、最終版のフレーム間隔は通常順 / 逆順で中央値 17 / 89ms、p95 54 / 197ms、p99 90 / 342ms、最長 207 / 516ms。250msを超えた回数は 0 / 45、500ms超 0 / 1、1秒超 0 / 0。同じ順序のV11足元版はp95 52 / 117ms、最長 177 / 408ms、V10はp95 51 / 163ms、最長 215 / 486msだった。V12の最長間隔516msに対応する観測窓でWebメイン 219.1、ラスター合計 981.5、合成 68.2 CPU msを要した（時刻照合誤差±60.1ms）。

描く姿勢と環境時刻を全版で固定すると、自然歩行・高負荷の計4,536間隔のうち250ms超は0回だった。森28体の同一9つのタッチを送った最終版は、通常順・逆順とも選択9 / 9件、実歩行開始3 / 3件、5秒以内到着3 / 3件。歩き始めた住民の開始遅延は中央値 41 / 45ms、最大 290 / 341ms。タッチは各幅・全住民を代表する成功率には換算できない。

8pxの退路に加え最後の3px退路も保護した最終試作では、同じ足・同じ指示から375pxの石像と430pxのきつねが8.01px歩いて到着した。390pxの石像では、近隣の最後の短い退路を守るため2つの指示を待機した。最終案の1区間の候補探索最大は全8観測で 2.01 CPU ms。独立に390px石像だけを再生した試験では最大2.58 CPU ms、WPEで40実秒の通常生活を追跡した候補1区間は最大4実msだった。

逆順のV12はV11足元版よりp95が80ms長く、180秒全体のラスター処理も404.38から485.06 CPU秒に増えた。最長間隔にはLinuxのCPU帯域制限による停止は記録されなかった。順方向では同じ2版のp95差は2msで、動き・環境時刻を全く同じにした試験では画像を描くコストにこの差は再現しなかった。長い間隔の候補は通常再生中の再描画・ラスター負荷で、個別の住民・装備・背景のどの描画が原因かは未分離。次は同じ端末でこの状態を採取し、画面を描き直した領域とリンクして確認したい。

実機iPhoneのSafari表示間隔・物理タッチ・発熱・GPU時間は未検証。各180秒の観測にはランナーと実際に選んだ行動の差があるため、フレーム性能の恒常的な改善や長時間停止の解消は確定できない。

## 原本と再測定

初版の8ジョブ、成長の追試1ジョブ、別枠で8pxを保護した中間版8ジョブ、最後の3pxも保護する最終版8ジョブ、同じモデルで終了条件を補正した1ジョブを別々に保存した。中間・最終の従来計測（statue.json・exit-guard.json）には候補探索が完了する前に観測が終わる行がある。その2ファイルを残し、候補CPUと閉塞の判定には05fe6a5cの完了補測を用いた。2つの生成済みモデル（通常席・参照席）のSHA-256は43bfaa7cと05fe6a5cでそれぞれ一致する。各ZIPのバイト数、GitHubが発行したSHA-256、ソースコミットは該当runのreceipt.jsonにある。 [5件の原本目録](https://naotocchi-mobility-v8-evidence.kerzion214.chatgpt.site/evidence/mobility-v12/performance/index.json)

公式CIと同じUbuntu・Node 24・Python 3.12で、下記の性能ワークフローの順序でホームを生成する。通常再生とタッチはPlaywright 1.62.0のWebKit。CI保存期限後の固定姿勢テープはV10原本のfixed・stressを復元し、各fixture.sha256と照合する。ローカルでprobeを追試する際は生成したゲームディレクトリを `MOBILITY_GAME` に指定する。[ソースとテープの再現手順](../home-mobility-v11/README.md#再現方法)
