# 本番ホームと候補のフレーム間隔・経路計算

本番 `384730f1` と、移動中の接触判定・指を離した位置の判定・同条件の住民画像再生成時の足元保持を含む候補を比較した。Linux WPE WebKit 26.5、375×615 CSS px、DPR 2。各地域で同じセーブ・正午・秋・晴れを使用し、開始3秒後から約60秒間、ブラウザー本来の requestAnimationFrame と単調時計で測った。各地域の両版を一台のGitHubランナーで交互に開き、会話や一時停止を含む自然な自動行動を観測した。最初は本番→候補→候補→本番、森28体と山10体の再試験は別のランナーで候補→本番→本番→候補。

通常再生では全体のMath.randomを合わせたが、本番の住民専用乱数はcryptoで別々に初期化された。固定ステップ試験では住民専用乱数にも同じ初期値を渡した。

森28体の初回正順では候補の1フレームが3.487秒空き、同じ時間帯の3.362秒を経路計算が占めた。個別照会の最大は212msで、少なくとも16回の照会が重なった。本番でも1.858秒の間隔に1.778秒・少なくとも10回の経路照会があった。山10体では両版とも最長フレームの大半が経路計算だった。一方、森1体の本番で発生した848msの間隔のうち、住民更新と重なった時間は1msであり、残る時間の要因は計測対象外。

## 同じモデル時間・入力での切り分け

両版で自然なフレームの代わりに0.1秒のモデル更新を600回実行した。同じ乱数初期値でホーム本体が生成した住民を動かし、照会のたびにモデル時刻、要求内容、全員の足元と大きさを記録した。同じ順番の照会のSHA-256を一件ずつ照合し、一致した要求だけの実測計算時間を比較した。壁時計上のフレーム間隔は上の通常再生で計測した。

共有Linux上でも森28体のモデル開始前に投影と足元が1.5秒安定するまで待ち、順番を反転して補試した。全4試行の開始状態は上記CIの一致した組と同一。両順とも本番は51要求・152.19px、候補は52要求・110.76pxとなり、終端状態もそれぞれCIと一致した。[補試記録](performance-forest-settled.json)

森28体では再試験で通常再生のp95差が縮んだ一方、4組すべてで歩いた距離が減少し、経路計算の累積時間が増加した。同じ時刻・要求・全住民位置を照合した31件の経路計算には大きな差が見られず、その後の要求と移動結果が変わった。山10体の1秒超停止は再試験で大小が逆転した。両地域とも、同じ入力1件あたりの計算と自然な再生中に発生する総仕事量を分けて評価する。

家庭ごとの経路数・歩行距離・会話のタイミングは通常再生の試行間で変わる。住民更新には移動・描画などが含まれ、経路計算はモデル更新の内数。これらの時間は足し合わせない。実機のiPhoneの描画完了、温度、電池消費は今回の測定範囲外。
